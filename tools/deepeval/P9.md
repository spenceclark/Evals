## Case is…, Grader is…, Run is…

**Case is** a `Golden` before the run and an `LLMTestCase` after it.
- The slice's `expected` dict has no Golden field. The expected action goes in `expected_output` and the rest goes in
  `additional_metadata`.
- `add_goldens_from_jsonl_file` can't read the slice: it wants a string in `expected_output`.

```python
extra = {"expected": row["expected"], "faults": row.get("faults", {})}
goldens.append(Golden(name=row["id"], input=row["input"], expected_output=row["expected"]["action"],
                      additional_metadata=extra, multimodal=False))  # fmt: skip
```

```python
return LLMTestCase(
    name=f"{golden.name}#{trial.rep}",
    input=golden.input,
    actual_output=trial.output.get("reply") or None,
    expected_output=golden.expected_output,
    context=[f"SHOP POLICY\n{v['policy']}", f"WHAT ACTUALLY CHANGED\n{v['happened']}"],
    tools_called=[ToolCall(name=e.name, input_parameters=e.args, output=e.result) for e in calls],
    token_cost=cost(trial.calls),
    completion_time=trial.latency_ms / 1000,
    metadata={"case_id": ..., "rep": ..., "action": ..., "also_ok": [...], "tool_turns": [...], "status": ...},
)
```

`completion_time` is recorded as 0: `supportdesk.run` leaves `latency_ms` unset.

`LLMTestCase` is shaped for a chat or RAG answer: `actual_output` is one string. The agent's structured close
(`action`, `order_id`, `amount`) has no field, so the reply goes in `actual_output` and the action goes in `metadata`.
The judge's five fields map onto DeepEval's like this:
- the email goes in `input`;
- the reply goes in `actual_output`;
- the tool calls and their results go in `tools_called`;
- the policy and "what changed" go in `context`, each with a label of ours.

`metadata` is never sent to the judge. Neither is `expected_output`, which holds the answer key.

**Grader is** a metric: a `BaseMetric` subclass with `measure`/`a_measure`, `score`, `threshold`, `success` and
`reason`. The code graders are custom metrics (score 1/0, threshold 1). The rubric is three `GEval`s, one per criterion:

```python
class ActionMetric(CodeMetric):
    metric_name = "action"

    def check(self, tc: LLMTestCase) -> tuple[bool, str]:
        m = meta(tc)
        got, want = m["action"], [tc.expected_output, *m["also_ok"]]
        return got in want, f"expected {' or '.join(map(str, want))}, got {got}"


JUDGE_SEES = [SingleTurnParams.CONTEXT, SingleTurnParams.INPUT, SingleTurnParams.TOOLS_CALLED,
              SingleTurnParams.ACTUAL_OUTPUT]  # fmt: skip

[GEval(name=name, evaluation_params=JUDGE_SEES, evaluation_steps=[FRAMING, text], model=model, strict_mode=True)
 for name, text in V2.criteria.items()]  # fmt: skip
```

**Run is** a pytest session that `deepeval test run` wraps.
- Each test calls the agent synchronously and asserts the metrics.
- DeepEval gathers every `assert_test` into one test run, prints it as a table, and writes it to
  `.deepeval/.latest_test_run.json`.
- `export.py` reads that file. The file is overwritten on every run, so `export.py` takes a path to a saved copy.

```python
@pytest.mark.parametrize("golden", GOLDENS, ids=[g.name or "" for g in GOLDENS])
def test_slice(golden: Golden, request: pytest.FixtureRequest) -> None:
    rep: int = request.node.callspec.params.get("__pytest_repeat_step_number", 0)  # pytest-repeat's 0-based index
    faults = meta(golden)["faults"]
    trial = supportdesk.run(golden.input, faults, case_id=golden.name or "", rep=rep, run_id=RUN_ID)
    tc = to_test_case(golden, trial)
    metrics: list[BaseMetric] = [ActionMetric(), LookedUpFirstMetric()]
    if tc.actual_output:  # no reply, no rubric verdict (the reference records null)
        metrics += rubric_metrics(JUDGE)
    assert_test(tc, metrics)
```

## Native vs glue

**Free:**
- the Golden → LLMTestCase model, with `tools_called` and `token_cost` fields;
- pytest parametrization over Goldens, and k=3 from a CLI flag;
- the run recorded to JSON, with every metric's score, reason, error and cost;
- the per-test console table, and a pytest exit code for CI;
- `BaseMetric`, so a code grader sits beside an LLM one;
- G-Eval's prompt and parsing;
- the judge's cost, once the price is given;

- skipping the judge when there's no reply;
- reading the repeat index from pytest-repeat's parametrization;
- `export.py`, which turns DeepEval's JSON into our shape: it strips G-Eval's " [GEval]" suffix from metric names and

## Trajectory access

The path grader reads `LLMTestCase.tools_called`: one `ToolCall(name, input_parameters, output)` per call, built from
`supportdesk.path.events(trial)` with `close_ticket` left out.

Two things `looked_up_first` needs have no field:
- **Which turn a call was in.** A lookup in the same turn as the refund doesn't count, because the model hadn't seen its
  result. The turns go in `metadata["tool_turns"]`, aligned with `tools_called`.
- **Whether it failed.** An error shows only as the `{"error": ...}` result. A call that never ran has `output=None`.

**Can DeepEval's own `ToolCorrectnessMetric` express the rule? No.**
- It scores `tools_called` against an `expected_tools` list: a set match, an exact match, or (with
  `should_consider_ordering=True`) an LCS weighted by length.
- Given the expected list `[get_order(A1), issue_refund(A1)]`, here it is on synthetic trajectories (`parity.py`, offline,
  default threshold 0.5):

```
trajectory                     reference  port  TC names  TC +args
lookup_then_refund                     P     P    P 1.00    P 0.67
lookup_only                            P     P    P 0.50    P 0.50
refund_without_lookup                  F     F    P 0.50    F 0.17
escalate_without_lookup                F     F    P 0.50    F 0.25
lookup_other_order                     F     F    P 1.00    F 0.17
failed_lookup                          F     F    P 1.00    P 0.67
lookup_and_refund_same_turn            F     F    P 1.00    P 0.67
refund_then_lookup                     F     F    P 0.50    P 0.50
stray_refund_then_good_pair            F     F    P 1.00    P 0.67
```

- **By name,** it passes all 7 bad trajectories.
- **With arguments,** it still passes 4 of them.
- **No threshold separates good from bad.** The good trajectory scores 0.67 with arguments, because only one of
  issue_refund's three arguments is in the expected call. A failed lookup, a same-turn lookup, and a stray refund before
  a good pair score 0.67 too.
- It rewards calls that are present. It has no notion of a call that came too early, of a lookup that failed, or of
  turns.
- It also needs a per-case expected list. A denial would expect `[get_order]` and pass a stray refund, since extra calls
  aren't penalised.
- So path is a custom metric.

**Parity:**
- **Recorded trials:** `parity.py` runs both custom metrics over every recorded trial in the main checkout's `runs/`:
  862 trials, of which the reference graders fail 29 on action and 5 on path. There are 0 disagreements with
  `supportdesk.graders.action` and `supportdesk.path.looked_up_first`.
- **Synthetic trajectories:** the port and the reference agree on all 9, including the ways to fail that the live run
  never hits.

## The judge

**What G-Eval sends:** one `user` message and no `system`.
- The only parameters are `max_tokens: 8192` and `model`. No temperature, `output_config`, `thinking` or effort is
  sent.
- `claude-haiku-5-5` isn't in deepeval 4.3.4's model table, so `supports_structured_outputs` is unset and DeepEval asks
  for JSON in free text.
- Haiku 5.5 thinks anyway, at its default effort. Across the 273 G-Eval calls in Vessel,
  `output_tokens_details.thinking_tokens` ran from 0 to 792 (median 149; 73 calls had none). Where there is a thinking
  block it is empty, with a signature. P4's judge pins effort to medium.

**Can G-Eval carry rubric v2? Mostly.**
- Three criteria, one pass/fail each: yes, as three `GEval` metrics. `strict_mode=True` is G-Eval's only binary form.
  It switches to the template above (score "STRICTLY EITHER 1 … OR 0") and forces the threshold to 1. The default form
  is a 0-10 score normalised to 0-1 against a threshold of 0.5.
- The rubric passes only if all three pass. That isn't a G-Eval feature; `export.py` computes it.
- G-Eval's own mode has the judge write its own evaluation steps from `criteria`, once per metric object (P0). Here
  `evaluation_steps` is pinned, so our wording is what's sent and no extra call is made.
- The `view()` fields all arrive, but in DeepEval's shape, not P4's:
  - **No system prompt.** Everything is one user message, and nothing marks the material as data. P4 fences each
    field in `<data>` tags.
  - **`context` is printed as a Python list repr.** Newlines are escaped to `\n` inside one long line, and the quoting
    changes from `"…"` to `'…'` depending on whether the text contains an apostrophe.
  - **Tool calls are printed as `ToolCall(...)` reprs.**
  - **The field names are DeepEval's** ("Input", "Actual Output", "Tools Called", "Context"). That is why we label the
    two context strings ourselves, and why the framing step exists (below).
  - **The template adds two instructions of its own:** to "follows the criteria 100%" and to "mention specific
    information from Context, Input, Tools Called, and Actual Output".

**How it parses the verdict:**
1. `trimAndLoadJson` reads the text (it copes with a ```` ```json ```` fence, which Haiku sometimes adds).
2. The result is validated as `ReasonScore{reason: str, score: float}`.
3. `success = score >= 1`.

A response that fails to parse is recorded as a metric `error` (`success: false`, score `null`). With `--ignore-errors`
that doesn't abort the test, but it does fail the test case.

**No-verdict rate: 19 of 270 free-text calls (7%).** That is 4, 4 and 11 across the three passes over 90 calls (the
two runs and the free-text re-judge below).
- All but one returned JSON with a `"reason"` and no `"score"`.
- One (`canc-01#2`, run 1) had an unescaped `"I'm sorry"` inside the reason string.

`export.py` records these as `rubric: null`. `evaluate()` aborts the whole run on the first one unless it is given
`ErrorConfig(ignore_errors=True)`.

## Repeats / pass@k

**Repeats are native; pass@k isn't.**
- `deepeval test run --repeat 3` runs each parametrized test three times via pytest-repeat. The repeat index reaches
  the test only through pytest-repeat's parametrization (`__pytest_repeat_step_number`, 0-based), which isn't a
  DeepEval API.
- Each repeat is a separate test case in the run (`name="elig-01#0"` etc.). Nothing groups them back by case.
- The run's summary is a pass rate over all 30 test cases. There is no pass@k or pass^k, and no per-case
  consistency.
- With repeats, the cache matters (read from source; `--use-cache` is off by default and wasn't tried). The cache key
  is `input`, `actual_output`, `expected_output`, `context` and `retrieval_context`; it does not include
  `tools_called` or `metadata`. Two trials with the same reply but different tool calls would share cached verdicts.

## Human review, CI story, hosting

**From using it:**
- `deepeval test run` prints a table per test case: each metric with its score, threshold, model, reason and error.
  That is enough to read a judge's reasons without opening a file.
- It exits with pytest's code: 1 in both runs, since any failed metric fails its test. That works as a CI gate, but an
  all-or-nothing one. A single flaky judge call or a judge parse error fails the build, and I found no pass-rate
  threshold in `deepeval test run --help`.
- The full record is the JSON in `.deepeval/`. Only the latest run is kept; each run overwrites it.
- Every run prints nudges toward Confident AI: "Run 'deepeval view' to analyze and save testing results on Confident
  AI", a "Note: Use Confident AI…" row in the table, and "No hyperparameters logged".

**From `--help` only, not exercised:**
- `deepeval inspect`, a local TUI over the saved run;
- `deepeval set-local-store sqlite`, which keeps more than the latest run;
- `deepeval gate`, a governance gate that needs a Confident AI policy;
- `deepeval view` and `deepeval login`, the hosted Confident AI.

There is no local human-labelling or annotation flow. `deepeval diagnose` shows "Not logged in" to Confident AI.

## Friction

In order, with the time each cost:

1. **pywin32 on Windows (15 min).** On the first `deepeval test run`, every pytest test failed with `AttributeError:
   'NoneType' object has no attribute 'test_cases_lookup_map'` in DeepEval's cache writer (pytest printed `F` for each).
   Yet DeepEval's own summary said "Pass Rate: 100.0% | Passed: 4".
   - The cause: portalocker can't take a shared lock on Windows without pywin32, so the cache read returns None. P0
     saw the same warning under `evaluate()`, where it was harmless.
   - Fix: `uv add "portalocker[win32]"`.
2. **pytest rootdir (5 min).** I first smoke-tested from a folder under `%TEMP%`. pytest walked up through the whole
   Temp folder, which made runs take 40 s and crashed one collection on a vanishing file. This is pytest, not DeepEval.
   `[tool.pytest.ini_options]` in this dir pins the rootdir and quiets a pytest-asyncio deprecation warning.
3. **The test case's shape (15 min).** There is no field for the structured close, no turn or error flag on
   `ToolCall`, and Goldens can't hold our `expected`. Everything went into `metadata`/`additional_metadata`.
4. **Our own bugs (10 min).**
   - `cap-t002` has no `faults` key.
   - `view()` raises KeyError on a trial with no `close_ticket`, so the adapter passes `reply=""`.
   Both were found by running: the second came from `parity.py` over old runs.
5. **pyright strict (10 min).**
   - DeepEval types `metadata`/`additional_metadata` as a bare `Dict`, so one ignore is needed.
   - `BaseMetric.__name__` is a property typed `Literal['Base Metric']`, so overriding it needs another.
   - Under pyright, `Golden(...)` needs `multimodal=` passed explicitly.
   - `evaluate`'s signature has an unresolved forward ref (P0).
6. **Judge form (25 min).** Run 1's 18/26 meant working out whether the cause was the replies or the judge, then the
   framing step and run 2.
7. **No structured output for Haiku 5.5 (20 min).** It isn't in the model table, so DeepEval knows no prices for it
   either. A model built without prices had `input_price=None` (offline). Reading the source, its cost would go
   unrecorded, but that wasn't run with real calls. Forcing structured output means setting an attribute on
   `model_data`, and `evaluate()` needs `ErrorConfig(ignore_errors=True)` to survive the free-text parse errors.
8. **Noise every run.**
   - `SyntaxWarning: 'return' in a 'finally' block` (PEP 765) at import;
   - pytest-asyncio's deprecation warning (until configured);
   - "No hyperparameters logged" and the Confident AI nudges.
9. **`deepeval diagnose` prints secrets.** Its output shows the last 6 characters of every `*_API_KEY` in the
   environment. It's meant as a config check, so it is easy to paste into a log or issue.

## What leaks

**LLM traffic (verified in Vessel).**
- Every request from the agent, the judge and the checks went through Vessel session 173: 726 requests, all backend
  `anthropic`, all model `claude-haiku-5-5`.
- The judge's requests carry only the user message, `model` and `max_tokens`. The SDK's headers are the same as the
  agent's (`traceparent` and `Authorization` come from the SDK or Vessel, not DeepEval).

**Telemetry (source and one snapshot, not a full capture).**
- PostHog (`https://us.i.posthog.com`) is on by default. In the source, `deepeval/telemetry/api.py` checks
  `telemetry_opt_out()` before each event it would send.
- Every command that imports deepeval ran with `DEEPEVAL_TELEMETRY_OPT_OUT=1`, except three runs of `export.py`
  (before the variable was added to its command above).
  - `export.py` imports deepeval (through `p9`), but it doesn't evaluate, call a metric, or run a CLI command.
  - Reading the source, importing deepeval with telemetry on only moves stray project files into `.deepeval/`. Events
    are sent from evaluation runs, CLI commands, login, the synthesizer and tracing. The PyPI version check runs only
    with `DEEPEVAL_UPDATE_WARNING_OPT_IN=1`.
  - So those runs most likely sent nothing, but that is read from the source, not captured.
  - The telemetry identity file (`~/.deepeval/.deepeval_telemetry.txt`) still has its Nov 12 timestamp.
- One `Get-NetTCPConnection` snapshot of the test process, taken mid-run, showed only loopback connections: Vessel on
  4550, plus asyncio's socket pairs.

**Confident AI (verified with `deepeval diagnose`).** "Not logged in", and no `deepeval view` or `login` was run. So
there were no uploads, only the nudges.

**Default judge (tried offline, not sent).** Any metric built without `model=` silently constructs DeepEval's default
judge, **OpenAI `gpt-5.4`**. `ToolCorrectnessMetric(...)` did, with no warning. This machine has `OPENAI_API_KEY` set,
so one metric missing `model=` would have sent the policy, emails and replies to OpenAI. Every metric here gets the
Haiku model explicitly.

**Local files.** `.deepeval/` (gitignored) holds the run JSON with every input, reply, tool output and judge reason,
plus a verdict cache. `deepeval setup` would download a setup wizard; it wasn't run.
