# P9 on Promptfoo

```bash
tools/promptfoo/run.sh
```

This runs `promptfoo eval -c p9.yaml` from `tools/promptfoo/`: the slice, k=3, three graders. It then writes
`p9_results.jsonl` from Promptfoo's own output file. Setup, once: `cd tools/promptfoo && npm ci && uv sync`. `run.sh`
loads the API key from the user environment if it isn't already set, turns off telemetry, update checks and sharing,
keeps Promptfoo's state in `tools/promptfoo/.promptfoo/`, and points the agent at Vessel if Vessel is recording.

## Run

- **Framework:** Promptfoo 0.125.1 (pinned in `package.json`), Node v24.21.0. The Python side is 3.14.7 in this
  folder's own uv project (`.venv`, `evals` editable from `../..`).
- **Eval:** `eval-TwQ-2026-11-16T18:28:24`, saved in `.promptfoo/promptfoo.db` and in `out/eval.json` (gitignored, 1.9 MB).
- **Cost: $0.042** for the full run.
  - Agent: $0.020 (75 Haiku calls). This is the provider's own `cost`, from `evalkit.core.cost`.
  - Judge: $0.022 (90 Haiku calls, 136,059 tokens in, 16,509 out, at $0.10/$0.50 per M). Computed by me from the token
    counts Promptfoo recorded.
  - Promptfoo prices the judge at $0: it logs `Using unknown Anthropic model: claude-haiku-5-5`, and its UI says "Total
    Cost: $0.02".
  - All the smoke runs together added under $0.01.
- **Wall time:** 88 s for `run.sh`; Promptfoo itself reports 1m 23s at concurrency 4.
  - About 6 s goes to the test generator (one Python spawn).
  - About 6 s goes to starting the provider's 4-worker Python pool.

## Case is…, Grader is…, Run is…

**Case.** A Promptfoo *test*: `{description, vars, assert, options, metadata}`.

- Promptfoo can read a tests file in `.jsonl` (`tests: file://x.jsonl`), but each line must already be a test in
  Promptfoo's shape. Tried with `tests: file://../p9/slice.jsonl` and the echo provider, which made no API calls:
  `Failed to load tests ...: Test case must contain assert, vars, options, metadata, provider, providerOutput,
  threshold, or only a description.`
- So a short Python generator (21 LOC) maps each slice row (`{id, input, expected, ...}`). It still reads
  `tools/p9/slice.jsonl`; nothing is copied by hand.
- `cap-t002` has no `faults` key, which the generator only found by crashing.

```yaml
tests: file://p9_tests.py:generate_tests
```
```python
{
    "description": r["id"],
    "vars": {
        "email": r["input"],
        "case_id": r["id"],
        "faults": r.get("faults", {}),
        "expected": r["expected"],
        "criteria": V2.criteria,
    },
    "metadata": {"suite": r.get("suite", ""), "tags": ",".join(r.get("tags", []))},
}
```

- The agent is a `providers:` entry, `file://p9_provider.py`, with `call_api(prompt, options, context)`.
- The `prompts:` template (`"{{email}}"`) is only a row label here; the provider reads the email from `context["vars"]`.

**Grader.** An `assert:` item. There is one of each kind:

- `javascript` (inline, action);
- `python` (file, path);
- an `assert-set` of three `llm-rubric` (the judge).

Each is tagged with a `metric`, which is what the export and the UI key on.

```yaml
- type: javascript
  metric: action
  value: |
    const got = context.metadata.trial.output.action;
    const ok = [context.vars.expected, ...(context.vars.expected.also_ok ?? [])].map((e) => e.action);
    return { pass: ok.includes(got), score: ok.includes(got) ? 1 : 0, reason: `expected ${ok.join(' or ')}, got ${got}` };
- type: python
  metric: path
  value: file://p9_path.py
- type: assert-set          # no threshold: passes only if all three pass
  metric: rubric
  assert:
    - type: llm-rubric
      metric: rubric.accurate
      value: "{{criteria.accurate}}"          # rubric v2's criterion text, from supportdesk.judges.V2 via vars
      transform: context.metadata.judge_input # the judge's input, built by the provider
    # ... rubric.no_outside_promises, rubric.tone the same
```

**Run.** An *eval*: the matrix prompts × providers × tests × `evaluateOptions.repeat`.

- It is stored as one row per (test, repeat) in SQLite under `$PROMPTFOO_CONFIG_DIR`.
- `-o out/eval.json` exports it.
- Each row has `testCase.description`, `repeatIndex`, `repeatGroupId`, `response` (output, `metadata`, cost), `success`,
  `namedScores` and `gradingResult.componentResults[]`.

## Native vs glue

**Native:**

- The test matrix, repeats and the concurrency pool.
- The per-assertion result tree, with named metrics.
- The LLM judge: its rubric prompt override, JSON verdict parsing and the grader provider config (effort, max_tokens,
  structured output).
- The `assert-set` ("all of these").
- Repeat stability stats.
- The JSON/SQLite record and the local viewer.
- A Python worker pool for the provider.

**Glue:**

- The provider, which runs `supportdesk.run` and ships the Trial over as JSON.
- The test generator, because Promptfoo's JSONL reader wants its own shape.
- The path assertion, because Promptfoo's trajectory assertions read OpenTelemetry spans, not provider output.
- The exporter.
- `run.sh`, mostly to switch off phoning home and to pin the Python interpreter.

## Trajectory access

- The provider returns the whole Trial (`dataclasses.asdict`, messages included) in `metadata.trial`.
- Promptfoo hands that metadata to assertions as `context.metadata`.
- `p9_path.py` rebuilds the Trial with `evalkit.core.trial_from_dict` and calls `supportdesk.path.looked_up_first`
  unchanged.
- Promptfoo's own `trajectory:*` assertions would need the provider to emit OTel spans to a local OTLP receiver (P0,
  from the docs). That wasn't tried, because the transcript was already there.
- Promptfoo has no "not applicable" result. A trial with no transcript would pass with reason `n/a: no transcript`,
  which the exporter turns into `null`. That never happened here.

## The judge

**Shape.**

- Three `llm-rubric` calls per trial, one criterion each, the same unit as the reference.
- They are grouped in an `assert-set`, which passes only if all three pass.
- The grader is `anthropic:messages:claude-haiku-5-5` with `effort: medium`, `max_tokens: 8000`, and
  `output_format: json_schema {reason: string, pass: boolean}`.

**Prompt.**

- `rubricPrompt: file://p9_rubric_prompt.json` is a `[system, user]` message pair.
- The system message is `supportdesk.judges.RUBRIC_SYSTEM_V0` byte for byte, with `{criterion}` replaced by
  `{{ rubric }}`.
- The user message is `{{ output }}`.

**Getting the view into the prompt.**

- The rubric prompt is rendered only with the test vars, `output` and `rubric`. Provider metadata isn't available
  there.
- An assertion-level `transform` does get `context.metadata`. So the provider computes
  `rubric_prompt(view(item, policy=SYSTEM_PROMPT), answer=False)` (the same `<data>`-fenced text P4's judge saw), and
  each `llm-rubric` swaps its output for that with `transform: context.metadata.judge_input`.
- A second route exists: give `output` as an object and write `{{ output.policy }}` and so on in the template. It is a
  trap. Promptfoo JSON-stringifies every object in the template context unless `PROMPTFOO_DISABLE_OBJECT_STRINGIFY=true`,
  so `output.policy` would render empty, silently. This is from the source (`processContextForTemplating`) and was not
  run.

**Checked on all 90 judge calls of the full run:**

- the rendered system message equals `V2.system.format(criterion=...)`;
- the user message equals the provider's `judge_input` (from `metadata.renderedGradingPrompt`, which Promptfoo stores
  on every judge result).

**What goes on the wire.** Captured with the Anthropic JS SDK's own logger (`PF_JUDGE_LOG=1` → `ANTHROPIC_LOG=debug`,
which shows `x-api-key` as `***`), on the capture run `--filter-pattern '^win-01$' --repeat 2`:

```
POST https://api.anthropic.com/v1/messages
body keys: model: 'claude-haiku-5-5', system: [Array], max_tokens: 8000, messages: [Array], stream: false, output_config: [Object]
headers: anthropic-beta: structured-outputs-2025-11-13, anthropic-version: 2023-06-01, user-agent: Anthropic/JS 0.133.0
```

- The full bodies (system text, user text, `output_config`) are in Vessel requests **19201–19203**.
- Those are the smoke-run judge calls that went through Vessel and got 400s (see Friction).
- Apart from `"temperature":0`, their bodies have the same shape as the direct calls (different case, elig-01).
- Their `output_config` was `{"format":{"type":"json_schema","schema":{...reason, pass...}},"effort":"medium"}`.
- No `thinking`, `temperature` (direct), `top_p`, `tools` or `metadata` is sent.
- The model still reasons: 3,642 reasoning tokens over 90 calls.

**The full prompt** (system and user, verbatim from `renderedGradingPrompt`, with the verdict) for win-01#2,
`no_outside_promises`, is in [`p9_judge_prompt.txt`](p9_judge_prompt.txt). Here is its user turn, with the policy cut:

```
<data name="shop_policy">
You are the customer support agent for Larkspur Supply, an online shop. Today is 2026-11-01.
...
<data name="agent_tool_calls_and_results">
call get_order({"order_id": "A2142"})
  -> {"id": "A2142", ..., "status": "delivered", "ordered_at": "2026-09-29", "delivered_at": "2026-10-01", ...}
</data>

<data name="what_actually_changed">
refunds issued: []
escalations made: []
</data>

<data name="reply_sent_to_customer">
Hello, thank you for contacting Larkspur Supply. ... If you'd like, reply with a photo of the missing part and your
order details, and we can look at other options for you.
</data>
```

**Parsing.**

- Promptfoo takes the first JSON object in the text; `pass` decides and `reason` becomes the assertion reason.
- With structured output on, all 90 verdicts parsed.

**Differences from the reference judge (`evalkit.judge`):**

- The schema field names are `reason`/`pass`, where ours are `critique`/`passed`. Promptfoo only reads `pass`/`score`.
  The system text still says "passed is true if…".
- A judge call that fails (API error, unparsable verdict) is a **fail** in Promptfoo, not an error. Its only marker is
  `metadata.graderError: true`, and the run summary says "0 errors". The exporter maps it to `null`.
- Promptfoo puts no `<data` escaping on the values. The escaping here comes from `rubric_prompt` in the provider.

## Repeats / pass@k

- **Repeats are native:** `evaluateOptions.repeat: 3` in the config, or `--repeat`.
  - Rows carry `repeatIndex` 0–2 and a `repeatGroupId`.
  - `testIdx` is renumbered across repeats, so the export keys on `description` and `repeatIndex`.
  - The provider's `context` gets `repeatIndex` (the keys it got were `bustCache, evaluationId, prompt, repeatIndex,
    test, testIdx, vars`), and passes it on as `rep`.
- **pass@k is not native.** Promptfoo reports "repeat stability" per group, on whole-test success:
  `results.repeatStability.groups[]` with `passRate`, a 95% CI and an `unstable` flag.
  - This run printed `10 repeated groups; 2 unstable`, with win-01 and dig-01 each at 2/3.
  - Derived from that: pass@3 = 10/10 cases and pass^3 = 8/10.
- Promptfoo's UI score for `rubric` is **97.78% (29.33/30)**, not 28/30. The `assert-set`'s named score is the *mean*
  of its three children, so a trial failing one criterion scores 0.67.
  - The row's pass/fail is right; the metric is not a pass rate.
  - The export reads the three criteria directly.

## Human review, CI story, hosting

**Used:**

## Friction

In order, with roughly what each cost:

1. **`npm ci`** took about 4 minutes, as P0 said. Running it in the background was fine.
2. **`uv init` joined the root workspace** (5 min).
   - It edited the root `pyproject.toml` and `uv.lock` to add `tools/promptfoo` as a workspace member.
   - I reverted that and re-ran it with `uv init --bare --no-workspace`, then `uv add --editable ../..`.
3. **Overwrote the spike's `provider.py`** (2 min). Restored it; the port's files are all `p9_*`.
4. **The test generator crashed** on `cap-t002`, which has no `faults` key (2 min).
5. **The judge got HTTP 400 through Vessel** (20 min). This was the big one.
   - `` `temperature` is deprecated for this model `` on all three judge calls. Vessel 19201–19203 show
     `"temperature":0` in the body.
   - Promptfoo strips sampling params for Claude 5+ in two ways: an explicit capability table, which has Opus 5.5 but
     **not Haiku 5.5**, and a `claude-*-5+` regex fallback.
   - The fallback only runs when the client's base URL host is `api.anthropic.com` (`allowsClaudeGenerationFallback`).
     Behind any proxy, Haiku 5.5 gets the default `temperature: 0` and is rejected.
   - P0 didn't hit this because it used Opus 5.5.
   - The fix: the judge goes direct to the API, and only the agent's calls go through Vessel.
   - **These 400s were scored as assertion fails, and the summary said "0 errors".**
6. **The interpreter for generators and Python assertions** (5 min).
   - The provider's `config.pythonExecutable` doesn't cover the test generator. Without `PROMPTFOO_PYTHON` it fell back
     to the system 3.10 and died with `No module named 'supportdesk'`. Tested.
   - The Python assertion uses the same `runPython` path, so it presumably falls back the same way; not separately
     tested.
   - `run.sh` sets `PROMPTFOO_PYTHON` to an absolute path.
7. **The export needed care** (10 min).
   - The row `error` field holds the failure *reason* on assertion fails, not just errors.
   - An `assert-set`'s children appear twice in `componentResults`, nested and flattened.
   - The `rubric` named score is a mean (see Repeats).

**The Python ↔ Node boundary.**

- **Node → Python:** the rendered prompt, the provider config and a `context`: vars, the whole test including its
  assertions, `repeatIndex`, `evaluationId`.
- **Python → Node:** `output` (the reply), `cost`, `tokenUsage` and `metadata`.
  - `metadata` holds the full Trial and the judge input, 4.4–7.3 KB of JSON per trial. Promptfoo writes it into the DB,
    the output file and the debug log.
  - Each Python assertion gets all of that back as `context`, re-serialized.
- **Time:**
  - About 6 s to start the provider's 4 persistent workers, which import `supportdesk` and `anthropic`.
  - About 6 s for the test generator.
  - A fresh Python process per path assertion (`wrapper.py`, not the pool): median 0.66 s, at most 0.77 s, over the 20
    I could pair in the log. That adds up to about 20 s across 30 trials, partly hidden by the concurrency.
- **Types:** none. Everything is JSON dicts on both sides. The JS action grader reads `context.metadata.trial.output`
  with no schema.

## What leaks

- **Off for this run:** telemetry (`PROMPTFOO_DISABLE_TELEMETRY=1`), the update check (`PROMPTFOO_DISABLE_UPDATE=1`),
  sharing (`PROMPTFOO_DISABLE_SHARING=1`, `--no-share`; the debug log shows `Wants to share: false`, `Shareable URL:
  null`) and remote generation (`PROMPTFOO_DISABLE_REMOTE_GENERATION=1`). With those set, the only host in the debug log
  is `https://promptfoo.dev`, in the printed "» Feedback" link. That is from the logs, not a packet capture.
- **Sent to Anthropic:**
  - The agent's 75 calls, through Vessel, session `p9-promptfoo`.
  - The judge's 90 calls, direct, so Vessel didn't see them. They were logged via the SDK on the capture run instead.
- **Written locally under `.promptfoo/`** (gitignored):
  - `promptfoo.db`, 2.9 MB with full transcripts.
  - `promptfoo.yaml`, with a generated user `id`.
  - A debug log on every run, about 490 KB, with every email and the provider's arguments.
- **Two unguarded invocations.**
  - While writing this up, I ran `promptfoo view --help` with none of the off-switches, and `promptfoo eval --help`
    with the switches but without `PROMPTFOO_CONFIG_DIR`.
  - Each created `~/.promptfoo/`: a `promptfoo.yaml` with a new generated user `id`, an empty `promptfoo.db`, and
    debug logs (388 bytes, no hosts). They are timestamped 18:31 and 18:32.
  - Whether `view --help` sent telemetry is unknown; I have no packet capture.
  - So **even `--help` writes an identity file to the home directory, and is not covered by the switches unless they
    are set.** I left `~/.promptfoo/` in place.
- **Downloads:** `npm ci` pulled 615 packages from the npm registry; nothing was downloaded at run time.
- No `sk-ant` string appears in `.promptfoo/` (DB, logs) or `out/`.
- With `PF_JUDGE_LOG=1`, the SDK's console log includes the Anthropic **workspace id** from the response headers. Keep
  that log out of the repo.
