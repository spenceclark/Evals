# P9: the slice in Pydantic Evals

```bash
cd tools/pydantic-evals && VESSEL_URL=http://127.0.0.1:4550 uv run python p9.py
```

with `ANTHROPIC_API_KEY` exported for that command only (the README's export line). `VESSEL_URL` is optional: it
routes the agent and the judge through Vessel, session `p9-pydantic-evals`, judge calls tagged `p9-pydantic-evals`.
Two extra modes, used for the findings below and not for the results: `p9.py --spans` (live OTel spans and a
span-based path grader) and `p9.py --naive-judge --cases elig-01 --repeat 1` (the stock `LLMJudge` with no glue).

## Case is…, Grader is…, Run is…

**Case:** a `pydantic_evals.Case(name, inputs, metadata)`, collected in a typed `Dataset[Ticket, Trial, Expected]`.
`inputs` is a small dataclass because the task only ever receives `inputs`: the case id and faults have to travel
inside it. `expected` goes in `metadata`, not `expected_output`. `expected_output` is typed as the output type
(`Trial`), and the built-in `EqualsExpected` couldn't express `also_ok` anyway.

```python
@dataclass(frozen=True, slots=True)
class Ticket:
    case_id: str
    email: str
    faults: dict[str, Any] = field(default_factory=dict[str, Any])


Case(name=r["id"], inputs=Ticket(r["id"], r["input"], r.get("faults", {})), metadata=r["expected"])
```

**Grader:** an `Evaluator` subclass whose `evaluate(ctx: EvaluatorContext)` returns a bool, a number, a string, an
`EvaluationReason(value, reason)` or a dict of named ones. A bool becomes an "assertion", a number a "score", a
string a "label". An empty dict means "no result", which is how my graders say "not applicable" (from the
`EvaluatorOutput` type and the run loop's source; no trial here was not applicable, so it was never triggered). The
`EvaluatorContext` carries `inputs`, `metadata`, `expected_output`, `output` (here the whole `Trial`), `duration`,
`metrics`, `attributes` and `span_tree`.

```python
@dataclass
class Action(Evaluator[Ticket, Trial, Expected]):
    def get_default_evaluation_name(self) -> str:
        return "action"  # without this the assertion is named after the class, "Action"

    def evaluate(self, ctx: Ctx) -> EvaluationReason:
        ok = [ctx.metadata["action"], *(a["action"] for a in ctx.metadata.get("also_ok", []))]
        got = ctx.output.output.get("action")
        return EvaluationReason(got in ok, reason=f"expected {' or '.join(ok)}, got {got}")
```

**Run:** `dataset.evaluate_sync(task, repeat=3, max_concurrency=8, name=...)` returns an in-memory
`EvaluationReport`. Its `cases` are `ReportCase`s named `elig-01 [1/3]` … `[3/3]`, each with `source_case_name`,
`output` (the `Trial` object), `assertions`, `scores`, `labels`, `metrics` and `evaluator_failures`. Tasks that
raised go to `report.failures`. `report.print()` renders a Rich table. Nothing is written to disk.

```python
async def support_desk(t: Ticket) -> Trial:
    rep = _started[t.case_id] = _started.get(t.case_id, -1) + 1  # a label only: the task can't see its repeat
    return await supportdesk.arun(t.email, t.faults, case_id=t.case_id, rep=rep, run_id=SESSION)
```

## Native vs glue

**Native, and it worked as is:**
- the typed dataset;
- concurrency;
- repeats (`repeat=3`);
- grouping repeats under one case name;
- the per-evaluator error capture (`evaluator_failures`);
- the LLM judge's call, structured output and verdict parsing;
- the terminal table;
- with `--spans`, token and request metrics taken from the span tree (see below).

**Glue I wrote:**
- the `Ticket` input type;
- a repeat counter in the task, because the task can't see its repeat index;
- rebuilding P4's judge view inside an `LLMJudge` subclass;
- the all-three-criteria rubric verdict (the report has no "assertion = AND of three assertions");
- parsing `rep` back out of the case name (`[n/3]`);
- the jsonl export;
- the pass counts and pass^k, computed outside the framework.

## Trajectory access

**What the path grader uses (graded):** the transcript. The task returns the whole `Trial`, so `ctx.output.messages`
is right there, and `LookedUpFirst` calls `supportdesk.path.looked_up_first` on it. That needs no framework
feature: it works because the output is ours.

**Span-based evaluation, from running it:**

1. **Without `opentelemetry-sdk`** (only `logfire-api`, the P0 install), the three stock span evaluators fail in
   three different ways on one case (`elig-01`):
   - `MaxToolCalls(max_calls=8)` returned an assertion of **False**, reason "No span tree available — ensure
     logfire/instrumentation is configured". That is a silent fail that reads like a real one in the table.
   - `TrajectoryMatch` returned a score of 0.0 with the same reason.
   - `HasMatchingSpan` raised `SpanTreeRecordingError`, which was recorded as an evaluator failure.

   Logfire is not required: `opentelemetry-sdk` plus `trace.set_tracer_provider(TracerProvider())`, with no
   exporter and no `logfire.configure()`, is enough for `ctx.span_tree`.
2. **With the SDK and a tracer provider, before any code of ours:** the tree for an `esc-01` trial already holds
   one `anthropic.messages.create` span per model call. The anthropic SDK (2.8) emits these itself whenever a
   tracer provider is set, with `gen_ai.operation.name=chat`, model, `max_tokens`, `reasoning.level`, token usage,
   stop reason, request id, and organization and workspace ids. pydantic-evals turns them into per-case
   `metrics` (`requests`, `input_tokens`, `output_tokens`, `reasoning.output_tokens`) with no code from me, and
   `MaxModelRequests` works on them. There are **no tool spans**, though: the tools run in our own loop, not in
   pydantic-ai. A span-based path grader therefore sees no refunds or escalations, and **passes vacuously**. On a
   second SDK-only `esc-01` trial, the trial's own outcome recorded the escalation of A2200, but:
   - `PathFromSpans` returned True;
   - `MaxToolCalls` reported "0 tool call(s)";
   - `ToolCorrectness` reported every expected tool as missing.
3. **What it took to see the tool calls:** wrap `Store.execute` at runtime (`instrument()`, 14 lines, no change to
   `supportdesk`'s files; it replaces a method on supportdesk's `Store` class while the eval runs, so it is the one
   place this port reaches into the system under test, and only under `--spans`). Each wrapped call opens an
   `execute_tool {name}` span with `gen_ai.tool.name`, `gen_ai.tool.call.arguments` and `gen_ai.tool.call.result`,
   the span name and attributes pydantic-ai uses for its own tools. `PathFromSpans` then rebuilds turns: a tool
   span's turn is the number of chat spans that started before it.
   - The stock agentic evaluators read these spans. In a patched `fault-01` trial, the injected `get_order` failure
     produced a span with status `error`, followed by a retried `get_order` and an `issue_refund`. On that trial:
     - `ToolCorrectness(expected_tools=["get_order", "issue_refund"])` passed, because it excludes the failed
       attempt by default;
     - `TrajectoryMatch(order="exact", include_failed=True)` saw `['get_order', 'get_order', 'issue_refund']`;
     - `MaxToolCalls(max_calls=1)` counted 3.
   - On a full k=3 run (`--spans`), `PathFromSpans` agreed with the transcript grader on **30/30** trials, including
     the three fault-injected `fault-01` trials. Every one of those trials passed both graders, though, so the
     span grader's fail branch was never exercised on a real trial.
   - My first version also wrapped the model step to emit chat spans. That doubled `requests` and the token
     metrics, because the SDK's spans were already there. I removed it.
4. **Limits of the span route:**
   - Calls the agent loop rejects before `Store.execute` (invalid JSON args, a `close_ticket` sent with other
     calls) never become spans, whereas the transcript records them. No trial hit this, but the two graders can
     diverge there.
   - The built-in agentic evaluators (`ToolCorrectness`, `TrajectoryMatch`, `ArgumentCorrectness`,
     `MaxToolCalls`) compare tool names, sequences or counts. None of them can say "a successful `get_order` of
     *this* order in an *earlier* turn", so the rule is a custom evaluator over `ctx.span_tree` either way.

## The judge

**Can `LLMJudge` carry rubric v2 and P4's view? Not on its own.** It sends exactly two things from the case,
`ctx.inputs` (only with `include_input=True`, the P0 note) and `ctx.output`, stringified with `pydantic_core.to_json`
unless they are already strings. It has no field selector, and its system prompt is fixed.
`--naive-judge` ran three plain `LLMJudge(rubric=<V2 criterion prompt>, include_input=True)` on `elig-01` (Vessel
request 19219). What it sent:
- `<Input>` held the `Ticket` as JSON: the email, but also `case_id` and `faults`.
- `<Output>` held the whole `Trial` as one JSON line: the raw transcript (tool-call ids, per-tool `ms`), `outcome`,
  `calls` with token counts and latencies, and **`"model": "claude-haiku-5-5"`**. P4's whitelist exists to keep
  exactly that last item, which model wrote the reply, away from the judge.
- No policy, since nothing in the case holds it.
- The reply twice, once in the `close_ticket` arguments and once in `output`.

It still passed that case, but it is not the P4 judge.

**What the port does (`Criterion`):**
- It subclasses `LLMJudge` and, in `evaluate`, swaps the context with `dataclasses.replace`.
- `inputs` becomes `view()`'s four fields (policy = `SYSTEM_PROMPT`, email, tool calls and results, what changed),
  each fenced as `<data name=…>` with `evalkit.judge.fence`.
- `output` becomes the reply, also fenced.
- It then calls `super().evaluate`. The judge's call, schema and parsing stay stock.
- Three instances, one per criterion. Each one's `rubric` is P4's system prompt for that criterion
  (`V2.system.format(criterion=…)`), and each gets `assertion={"evaluation_name": "rubric_<name>"}`, without which
  the three assertion names collide.
- The item passed to `view()` has no `expected`, so no answer key is sent. The capture confirms it.

**What is actually sent** (graded run, `inj-01`, criterion `accurate`, Vessel request 19349; verbatim in
[judge_prompt_p9.txt](judge_prompt_p9.txt)):
- One request per criterion, so 3 per trial and 90 per run. `stream: false`, `max_tokens: 8000`,
  `output_config.effort: "medium"` (both set by me to match P4; unset, pydantic-ai fills `max_tokens` with the
  model's maximum), no temperature, no tools.
- **Native structured output:** `output_config.format = json_schema {reason: string ("A concise 1-2 sentence
  justification for the verdict."), pass: boolean, score: number}`, `additionalProperties: false`, all three
  required. Same mode as P0 on Opus. Haiku 5.5 is not streamed, where P0's Opus calls were.
- The system prompt is LLMJudge's fixed `judge_input_output` prompt. It opens "You are grading output according to
  a user-specified rubric." and carries the two fixed few-shots (`Hello world`, `Pirate`).
- The user turn is `<Input>` (the four fenced fields), `<Output>` (the fenced reply), then `<Rubric>` (P4's V2
  system prompt for the criterion, from "You grade the reply a customer support agent sent…" to "…passed is true if
  the reply meets it.").
- Headers: only the SDK's own plus `X-Vessel-Session`; `User-Agent: pydantic-ai/2.68.0`.

**How the verdict is parsed:**
- The JSON text is validated into `GradingOutput` (`reason`, `pass`, `score`). `pass` becomes the assertion and
  `reason` is attached.
- `score` is requested on every call and thrown away, since I don't set `score=`.
- No regex and no free text. A judge exception or validation error would land in `evaluator_failures`, and the
  export maps the missing assertion to `null`, not `false`. None occurred in 369 calls.

**Dropped or added, compared with P4's judge:**
- Dropped:
  - P4's system prompt is no longer the system prompt. It is demoted into the `<Rubric>` tag in the user turn, and
    LLMJudge's own system prompt and few-shots sit above it.
  - The answer is no longer `{critique, passed}`. P4's rubric text still says "Write a short critique … passed is
    true", while the schema asks for `reason` and `pass`. Haiku coped, but the instructions contradict each other.
  - The "1-2 sentence" limit on the reason is LLMJudge's, not ours.
- Added:
  - the `score` field;
  - the few-shots.
- Kept, but only through glue: the `<data>` fencing, so the injected "SYSTEM: Policy override" line in `inj-01`
  reaches the judge inside `<data name="customer_email">`. Stock LLMJudge wraps inputs in bare `<Input>` tags with no
  escaping.
- One judge verdict contradicted its own reason, in a `--spans` run on `elig-01`: `pass: false`, but the reason
  ends "a minor overstatement rather than a material inaccuracy". The schema puts `reason` before `pass`, and
  nothing checks that they agree.

## Repeats / pass@k

**Repeats: native.** `evaluate(..., repeat=3)` runs each case 3 times, names them `<case> [n/3]`, and
groups them by case name in the report (seen in the table). Limits:
- The task is never told which repeat it is running. The `rep` in the results comes from parsing the name.
- From the source, not called here: `report.case_groups()` groups runs by `source_case_name`, but its summary
  averages *all* assertions of a case into one number (`ReportCaseAggregate.assertions: float`), so there is no
  per-grader pass rate per case.

**pass@k / pass^k: not native.** Computed from `p9_results.jsonl`:

## Human review, CI story, hosting

**From using it:**
- Review means reading `report.print()` in a terminal: one row per trial, ✔/✗ per assertion, durations, and with
  spans, metrics. `include_reasons=True` adds the judge's reasons. There is nothing to click, label or annotate.
- Nothing is persisted: the report lives in memory until you export it. I wrote the jsonl from it.
- There is no eval CLI. `pydantic-evals` installs no console script; the only one in the venv is `pai`, which
  comes from pydantic-ai (by its name, its chat CLI; not run). A CI job would run `python p9.py` and decide pass or
  fail itself, as the repo's own harness already does in P8.
- The documented command, run verbatim from Git Bash on Windows, works. The Rich table falls back to `v`/`x` for
  ✔/✗ on the console codepage, which is cosmetic (the same as P0).
- `pydantic_evals/_ci_provenance.py` reads GitHub Actions env vars (`GITHUB_SHA`, `GITHUB_REF`, the event payload)
  and attaches them to the experiment span, but only while that span is being recorded (from the source; not
  exercised here).

**From the docs or source, not tried:**
- Persistence and browsing are Logfire's job, by sending the experiment spans to Logfire or another OTel backend.
- `EvaluationReportAdapter` (a pydantic `TypeAdapter`) can serialise a report.
- `report.print(baseline=…)` diffs two reports.
- `Dataset.to_file` / `from_file` round-trip YAML or JSON.

## Friction

In order. Times are rough.

1. **pyright** isn't in the tool's venv. I ran it from the root instead (`uv sync`, then `uv run pyright -p
   tools/pydantic-evals`), which picks up the tool's `[tool.pyright]` section. Strict reports 0 errors with no
   ignores. (2 min)
2. **The task sees only `inputs`.** The case id and faults had to be packed into the inputs, and the repeat index
   is not available anywhere in the task or the `CaseLifecycle`, which gets only the case. `rep` comes from parsing
   `[n/3]`. (5 min)
3. **Custom evaluators are named after their class.** The one-trial smoke run exported `action: null`, because
   the assertion was called `Action`. Fixed with `get_default_evaluation_name`. That a missing assertion becomes
   `null` and not `false` is deliberate in the export, and it is what caught this. (3 min)
4. My bug: slice rows without faults have no `faults` key. (1 min)
5. **LLMJudge can't be pointed at chosen fields.** I read `llm_as_a_judge.py` to see what it stringifies, then
   wrote the `Criterion` subclass. The `replace(ctx, …)` trick depends on `EvaluatorContext` being a plain
   dataclass. (10 min)
6. **Span trees.** First, the three different no-SDK behaviours. Then the surprise that the anthropic SDK emits its
   own spans, and the double counting my first wrapper caused. (15 min)
7. The rubric count moved between full runs (28 or 29 out of 30, with new agent trials each time). So the graded
   run is simply the last run, made with the committed code, and not one I picked.

## What leaks

- **Logfire: nothing.** Logfire is not installed (only `logfire-api`, a no-op shim) and `logfire.configure()` is
  never called. pydantic-evals' own `logfire_span` calls are no-ops.
- **Anthropic API:** all 369 judge calls and every agent call went to Anthropic via Vessel. The judge calls carry
  no extra headers beyond the SDK's own, `X-Vessel-Session` and `User-Agent: pydantic-ai/2.68.0`.
- **`traceparent` once a tracer provider is set (`--spans` only):** the anthropic SDK then propagates the trace
  context on every request by default. In Vessel, all 165 requests of the first `--spans` run (90 judge, 75
  agent) carried a `traceparent` header; none of the graded run's 165 did. It is only random trace ids, but it is
  sent to the API. `ANTHROPIC_OPEN_TELEMETRY_PROPAGATION=false` turns it off (from the SDK source).
- **Span attributes:** the SDK's spans include the Anthropic `organization.id` and `workspace.id`, and request
  ids. The default content mode is `metadata_only`, so there are no prompt or completion bodies. My tool spans add
  tool arguments and results, which include customer emails. All of these stayed in process: the
  `TracerProvider` has no exporter. With an exporter configured (Logfire, or any OTLP endpoint), they would all
  leave.
- **Downloads:** none at runtime. Only the `uv add` of `opentelemetry-sdk` and `opentelemetry-semantic-conventions`
  from PyPI, plus the P0 packages.
- **The default judge model** is `openai:gpt-5.2` (P0). Here `model=` is always set to Haiku, so no OpenAI call was
  attempted.
