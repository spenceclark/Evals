# P9 in Langfuse (`langfuse` Python SDK, Langfuse Cloud, EU region)

```bash
cd tools/langfuse && export ANTHROPIC_API_KEY="$(powershell.exe -NoProfile -Command "[Environment]::GetEnvironmentVariable('ANTHROPIC_API_KEY','User')" | tr -d '\r\n')" && export LANGFUSE_PUBLIC_KEY="$(powershell.exe -NoProfile -Command "[Environment]::GetEnvironmentVariable('LANGFUSE_PUBLIC_KEY','User')" | tr -d '\r\n')" && export LANGFUSE_SECRET_KEY="$(powershell.exe -NoProfile -Command "[Environment]::GetEnvironmentVariable('LANGFUSE_SECRET_KEY','User')" | tr -d '\r\n')" && export LANGFUSE_BASE_URL=https://cloud.langfuse.com VESSEL_URL=http://127.0.0.1:4550 && uv run python p9.py run p9-run-1 && uv run python p9.py export p9-run-1
```

`run NAME` makes one experiment with that exact name. Langfuse derives the experiment's id from the project, the
dataset and the run name, so a second `run` with the same name would **add** its trials to the first. `run` refuses a
name that already exists. To repeat the command above, pick a new name.

Other subcommands:

- `p9.py dataset` uploaded the slice as the project's `p9-slice` dataset (upsert by item id).
- `p9.py run p9-run-2` made the second experiment.
- `p9.py export p9-run-2 --out p9_results_run2.jsonl` exported it.
- `p9.py compare p9-run-2 p9-run-1` prints each run's per-case pass rates from the stored scores.
- `p9.py queue p9-run-1` put two trials in an annotation queue.
- `p9.py review smoke-1 [--rep N]` adds one human score through the SDK and shows what is stored next to the
  evaluator's.

`probes.py` holds the model-free checks: `reps`, `path-synth` and `errors`. Its `bare` probe runs one agent trial.
`audit.py` reads a run back and checks what was stored. Neither is part of the port.

`queue` and `review` were last run before a typing-only refactor and were not re-run afterwards, since both write to
the project. `dataset`, `run` (its name guard), `export` and `compare` were re-run on the final code.

`VESSEL_URL` is optional. The agent and the judge both run locally on the Anthropic API. Langfuse receives
OpenTelemetry spans and the REST calls for datasets and scores.

**Which file is which.**

- `p9_results.jsonl` is run 1 (`p9-run-1`), the record run. `p9_results_run2.jsonl` is run 2 (`p9-run-2`), which
  exists for the comparison. Both are exported from what Langfuse stored: the experiment's items (input, output,
  metadata), the scores on each trace, and each trace's observations.
- `p9_judge_prompt.txt` is one judge request as sent (Vessel 21784, run 1).

## Case is…, Grader is…, Run is…

**A case is a dataset item.**

- `p9.py dataset` writes each slice line as a `DatasetItem`:
  - `input = {"email"}`;
  - `expected_output` = the whole expected dict, which the evaluators see as `expected_output`;
  - `metadata` = case id, faults, suite and tags.
- The item id is `uuid5(NS, case_id)`, so a re-upload upserts. Langfuse ids must be unique across datasets.

```python
lf.create_dataset_item(
    dataset_name=DATASET,
    id=str(uuid.uuid5(NS, r["id"])),
    input={"email": r["input"]},
    expected_output=r["expected"],
    metadata={"case_id": r["id"], "faults": r.get("faults", {}), "suite": r["suite"], "case_tags": r["tags"]},
)
```

- **A re-upload with unchanged content made a new version of every item.** `version` and `created_at` both moved to
  the re-upload time, and there were still 10 items. LangSmith did the same.
- That re-upload happened after the record runs. So the items' current version postdates both runs, and Langfuse has
  no record of which version they ran against.
- The runs don't record which version they used: `experimentItemVersion` is `null` on every item. `run_experiment`
  sends it only through a private `_dataset_version` argument.

**The task** is `async task(*, item, **kwargs) -> output`.

- The runner passes the `DatasetItem` and no repetition index.
- The task calls `supportdesk.arun` and replays the tool calls as `tool` observations (see Trajectory).
- It writes `rep`, `status`, `tool_observations` and the SUT cost into the task span's metadata.
- It returns the close_ticket call **plus the transcript and the store outcome**. An evaluator gets only `input`,
  `output`, `expected_output` and the dataset item's `metadata`; there is no handle on the trace or the run. So
  whatever a grader needs from the trial has to be in the output.

```python
trial = await supportdesk.arun(item.input["email"], item.metadata["faults"], case_id=case_id, rep=rep, run_id=...)
lf.update_current_span(
    metadata={
        "rep": rep,
        "status": trial.status,
        "tool_observations": replay_tools(trial.messages),
        "sut_cost_usd": cost(trial.calls),
    }
)
return {**trial.output, "messages": trial.messages, "outcome": trial.outcome}
```

**A grader is an evaluator.**

- It is a function `(*, input, output, expected_output, metadata, **kwargs) -> Evaluation | list[Evaluation]`, sync or
  async.
- Each `Evaluation(name, value, data_type, comment, metadata)` is stored as a **score** on the trial's task
  observation, with `source: API`. Here they are `BOOLEAN`.
- All three graders put `metadata={"grader": "p9"}` on their scores. That is the only thing that tells them from a
  human score made through the SDK, which is also `source: API` (see Human review).
- **A raising evaluator is caught** (`probes.py errors`). Its observation gets `level: ERROR` and the exception's text
  as `status_message`, and no score is stored. The port never sends a `None` value (not tried): "no verdict" is no
  score.
- The declared `EvaluatorFunction` type says `metadata: Dict | None`, so strict pyright rejects evaluators typed
  `metadata: JSON`. The list is typed `list[Any]`.

```python
def action(*, input: JSON, output: JSON, expected_output: JSON, metadata: JSON, **kwargs: Any) -> Evaluation:
    ok = [expected_output["action"], *(a["action"] for a in expected_output.get("also_ok", []))]
    got = output.get("action")
    return Evaluation(
        name="action", value=got in ok, data_type="BOOLEAN", comment=f"got {got}, accepted {ok}", metadata=GRADER
    )
```

**A run is an experiment** (in the API also "dataset run").

- It comes from `lf.run_experiment(name=..., run_name=..., data=items * 3, task=..., evaluators=[...],
  max_concurrency=10, metadata={...})`.
- Each trial is one **trace**:
  - `experiment-item-run` → `experiment-item-task`, with the SUT's generations and the replayed tools under it;
  - `experiment-item-evaluation` → one `EVALUATOR` observation per evaluator, the judge's generations under
    `rubric_v2`.
- Unlike LangSmith, the judge's calls live in the trial's own trace.
- The SDK docstring is explicit: "Experiment runs are recorded only through the exported traces; no separate dataset
  run is created via the API". The experiment is the set of traces carrying `langfuse.experiment.id`.
- `run_experiment` returns an `ExperimentResult`: `item_results`, each with its evaluations and `trace_id`, plus
  `experiment_id` and `experiment_url`. It flushes before returning.
- Reading back: `api.experiments.list(name=...)` and `api.experiments.list_items(experiment_id=...)`, then
  `api.scores.get_many(trace_id=..., fields="details,subject")` and `api.observations.get_many(trace_id=...)`.

## Native vs glue

**Free from Langfuse:**

- hosted datasets with item versions;
- `run_experiment`: concurrency, a trace per trial, evaluator isolation, evaluator observations, scores;
- **the SUT's and the judge's model calls as generations, with no wrapper.** The Anthropic SDK emits its own span per
  call whenever a tracer provider is registered, and Langfuse registers one (see Trajectory). One env var adds the
  content;
- model pricing (Haiku 5.5 known server-side), per-generation cost, and per-run cost and latency;
- the experiments list with per-run score counts;
- the comparison view;
- annotation queues;
- `create_score` for human review;
- the trace UI.

**From supportdesk (no Langfuse judge library used):** P4's judge, `supportdesk.judges.rubric` with
`evalkit.judge.Judge`, and the reference `looked_up_first`, both called as-is from evaluators.

**Glue:**

- `replay_tools`;
- the repetition counter;
- putting the transcript into the task output;
- the per-run judge cache;
- the read-back export (pagination, raw-string I/O, per-trace scores, transcript rebuild, cross-checks);
- `compare`, `queue` and `review`;
- the CLI.

As in Braintrust and LangSmith, the export is the largest piece. The data is all there, but getting "one row per
trial" means:

1. List the experiment's items. Their `input` and `output` come back as JSON **strings**, and their metadata comes back
   flattened, with string values (`"rep": "1"`).
2. Fetch each trace's scores separately: the items' own `scores` field has no metadata, comment or subject.
3. Fetch each trace's observations, to cross-check and price.

## Trajectory access

**With no help, Langfuse got the SUT's model calls but not its tool calls.** `probes.py bare` ran a task that only
calls `supportdesk.arun`, with the Anthropic SDK at its default. The trace held:

- `experiment-item-run` and `experiment-item-task`;
- **three `GENERATION` observations named `anthropic.messages.create`**.

The generations came from the **Anthropic SDK's own OpenTelemetry tracing** (scope `com.anthropic.sdk.python`,
`anthropic 2.9.0`).

- The SDK starts a span for every API call when an OTel tracer provider is registered. Langfuse registers one globally
  when it starts. Its export filter keeps spans that have `gen_ai.*` attributes, and these do.
- So the agent's model calls nest under the task span by contextvars, with nothing installed or wrapped. The same goes
  for the judge's calls under `rubric_v2`.
- **By default the spans carry no content** (`content_mode: "metadata_only"`): model, `max_tokens`, effort, tokens,
  stop reason, response and request ids, the URL, and the Anthropic organization and workspace ids. The stored
  generations had 0 characters of input and output (`probes.py bare`).
- `ANTHROPIC_OPEN_TELEMETRY_TRACES_CONTENT_MODE=content` adds the messages. `p9.py` sets it before any client exists.
  Then each generation stores its input and output in the GenAI semantic-convention shape:
  - the input is a list of messages with **the system prompt as a leading `{"role": "system"}` message** (on the wire
    `system` is still a string);
  - then `parts` of type `text`, `tool_call` and `tool_call_response`;
  - the tool definitions are not stored.

**Tool executions are not observations unless we make them.** supportdesk runs its tools in its own loop, so
`replay_tools` writes each tool call that ran as a `tool` observation:

```python
with lf.start_as_current_observation(name=c["name"], as_type="tool", input=c["args"], metadata=meta) as o:
    o.update(output=r["result"], level="ERROR" if r["error"] else "DEFAULT")
```

**The path evaluator reads the transcript from the task output**, because an evaluator gets nothing else.

- `path` builds a `Trial` from `output["messages"]` and calls the reference `looked_up_first` unchanged. This is the
  only port where path is the reference function itself, not a rewrite.
- It does not read the trace back. Evaluators run inside the trial's root span, before it ends, and Langfuse's API
  serves data after ingestion, so a read-back would race (Braintrust's failure).
- The cost: the transcript is stored in the task span, the root span and each of the three evaluator observations'
  inputs. That is five copies per trial.

**Checked on failing paths, through the hosted service** (`probes.py path-synth`). Six synthetic transcripts went
through a model-free hosted experiment with the port's `replay_tools` and `path`. For each, the stored `path` score,
`looked_up_first` on the original, and `looked_up_first` on a transcript rebuilt from the **stored** tool observations
all agreed with the known answer:

- fail: refund before any lookup;
- fail: lookup and refund in the same turn;
- fail: errored lookup, then refund;
- fail: lookup of a different order, then escalate;
- pass: ids reused across turns and order id `" a1 "`;
- pass: a refund listed after `close_ticket` that never ran.

**On the record runs,** `export` rebuilds each transcript from the stored tool observations. It checks:

- the reference `action` and `looked_up_first` agree with the stored scores on all 60 trials;
- the number of stored tool observations matches the count the task wrote, on all 60.

## The judge

**P4's own judge, run locally inside a Langfuse evaluator.** Langfuse has no client-side LLM-as-judge of its own.

- **Its native judge runs server-side** (the "Evaluators" page: LLM-as-a-judge templates the Langfuse worker runs on
  new traces or experiments). It calls the model through a project LLM Connection, which means storing a model key in
  Langfuse.
- **Not used, by decision:** the Anthropic key stays local. So P0's open question isn't answered: whether that judge
  sends a forced `tool_choice` that fails on Claude.
- The SDK's only client-side judge path is `create_evaluator_from_autoevals`. It calls an autoevals scorer
  synchronously, and would bring autoevals' OpenAI-wire defaults (Braintrust's gateway finding). Not used.

`rubric_v2` calls `supportdesk.judges.rubric(judge, JudgeModel("claude-haiku-5-5"), V2, view(item, policy=SYSTEM_PROMPT),
answer=False)`.

- That is three calls, one per criterion, each a `messages.parse` with P4's system prompt, the `Verdict` schema and
  effort medium.
- It returns `rubric` (true only if all three pass) and the three criteria, with each critique as the score's comment.
- A criterion without a verdict yields a `<criterion>_error` score and no `rubric` score, never a fail. That never
  happened.
- `view()` sees the policy, the email, the tool calls and results, what changed and the reply: no answer key.

**What it sends** (Vessel request 21784, in full in `p9_judge_prompt.txt`):

| Param | Value | From |
| --- | --- | --- |
| system | P4's rubric system prompt with the criterion | `RUBRIC_SYSTEM_V0.format(criterion=...)` |
| user | P4's user block: `<data>` fences around the policy, email, tool calls and results, what changed, the reply | `rubric_prompt(view(...), answer=False)` |
| output_config | `{"effort": "medium", "format": {"type": "json_schema", "schema": Verdict}}` (critique: string, passed: boolean) | `messages.parse(output_format=Verdict)` |
| max_tokens | 8000 | `JudgeModel` |
| tools / tool_choice / temperature | not sent | |
| headers | `traceparent`, `baggage: langfuse_trace_id=…` added (see What leaks) | the Anthropic SDK's OTel propagation |

The system prompt opens: "You grade the reply a customer support agent sent to a customer, against ONE criterion."

**Verdict parsing:** the SDK parses the JSON text into `Verdict`. A `max_tokens` stop, a refusal or a parse failure
would become a status, not a fail (`evalkit.judge`).

**Recorded in Langfuse, exactly.** `audit.py p9-run-1` compared the 90 stored judge generations with P4's judge
cache:

- every stored input (system message plus user text) equals the `(system, prompt)` that was asked, byte for byte;
- every stored output equals the verdict text the model returned;
- the stored generation drops the schema: only `gen_ai.output.type: "json"` says structured output was asked for.

**Repeats and the cache.** `Judge` caches by prompt, so each run gets a fresh cache file
(`logs/judge-<run>.jsonl`, gitignored). Otherwise run 2 would silently reuse run 1's verdicts for identical replies.
Within a run, no two trials sent the same prompt: 90 calls each.

## Repeats / pass@k

**Not native.** `run_experiment` has no repetitions parameter. The port passes the dataset items three times
(`data=items * 3`) and counts repeats itself.

- `probes.py reps`: one item twice in one call gives **two items in the experiment with the same `experimentItemId`**
  (the dataset item id), each its own trace and scores. Nothing collapses.
- The stored data keeps all 30 trials, and the experiments list counts them (`true: 29, false: 1`).
- **The comparison view shows one trial per dataset item**, the most recently started one: rep 2 in both record runs,
  because `items * 3` queues each case's third trial last.
  - The other two can't be reached from that view. The side peek's pager steps between the experiments in view, not
    between trials, and disappears with only a baseline.
  - The Display menu's layouts (grid, list, score matrix), diff modes and item visibility don't change this; list view
    showed the same values.
  - Its "SUMMARY · this page (10 items)" is computed over those 10 shown trials, not the 30 (see the comparison).
  - The trials are reachable through the trace list, or through the API.
- The repetition index exists only because the task writes `rep` into the span metadata.
- pass@3 / pass^3 would be glue over the export.

## The experiment comparison (hosted)

**How it is set.**

- `run_experiment` prints a link to the experiment's results page. In the UI, an experiment is the **baseline** and
  others are added under **Compare**. The page then shows one row per dataset item, with each run's scores side by
  side.
- `run_experiment` takes no baseline, and no API returns a comparison or a per-experiment aggregate. The public
  metrics API can't group scores by experiment.
- `p9.py compare` therefore recomputes per-case means over all trials from the stored scores.

**What it showed for run 1 against run 2 as baseline** (UI, read-only, through Claude in Chrome, already signed in):

- **The summary row:** per score, "% true" for each run, a delta (`+0.10`) and counts of rows that went up or down
  (`↗ 2 ↘ 1` for `rubric`).
- **The rows:** each run's score values for the trial shown. Changed cells are marked `↻`.
- **The numbers are over one trial per item, not three.** The summary is labelled "this page (10 items)":
  - it gave **run 2 `rubric` 80% true and run 1 90%**, where the true rates are 27/30 = 90% and 29/30 = 96.7%;
  - it showed `win-01` and `dig-01` failing in run 2 and `cap-t002` failing in run 1. Each is that case's rep 2, the
    latest-started trial (checked against the stored start times). `win-01#1`'s fail in run 2 isn't visible there;
  - so a comparison of k=3 runs compares two samples of 10, and which trial represents a case depends on scheduling
    order.
- **The experiments list is right.** Per run it gives score counts over every trial (`rubric` false 1 / true 29 and
  false 3 / true 27), latency, cost and an **Error Count**.
- Error Count was **2** in both runs. It counts dataset items with an observation at `level: ERROR`: here `fault-01`
  (its injected 503s) and `elig-01` (a `close_ticket` the loop refused).
  - Those levels are set by `replay_tools`, so whether a tool error is an "experiment error" is the port's choice.
  - Set as here, an injected fault shows up as experiment errors, as in Braintrust and unlike LangSmith.

**How it treats run-to-run noise:**

- **No noise model.** Any difference between the shown trials is an up or down arrow, and the summary shows a delta.
  There are no intervals or tests.
- Identical-config reruns gave `rubric ↗2 ↘1`, `accurate ↗1 ↘1` and `no_outside_promises ↗1`.
- **Sampling makes it worse:** with one trial per item shown, a case that fails 1 of 3 times can show as a pass or a
  fail depending on which trial started last.
- Cost and latency appear per run in the list (Ø 5.17 s vs 4.38 s, $0.0399 vs $0.0400), with no regression marker.

**No lag seen.**

- Langfuse's own SDK docstring warns that public endpoints other than OTel ingestion, observations v2 and metrics
  "can delay data by about 10 minutes".
- Here the experiment items, scores and observations were complete when read 15 s (probes) to 1–5 minutes (exports)
  after the runs. The UI counts were complete when first looked at, about 7 minutes after.
- Unlike LangSmith's 14-minute lag on `feedback_stats`, nothing read partial. But nothing was read in the first 15 s
  of a record run, and a model-free probe read 0 items for the first ~10 s.

## Human review, CI story, hosting

**A human score through the SDK, tried** (`p9.py review smoke-1`, on the throwaway smoke run, so the record runs keep
only evaluator scores):

- `lf.create_score(trace_id, observation_id=<task span>, name="rubric", value=False, data_type="BOOLEAN", ...)` stores
  a second `rubric` score on the same observation. It is **`source: API`, the same as the evaluator's**.
- Nothing links or ranks the two. Only the `metadata` the port added (`{"grader": "p9"}` vs `{"by": "human"}`) tells
  them apart, and the default score listing doesn't return metadata (`fields=details` is needed).
- **What it does to the numbers (UI):**
  - the comparison view's summary for `smoke-1` went from `rubric` 100% to **50% true** over its one shown item: the
    human 0 and the evaluator's 1, **averaged** (as in Braintrust and LangSmith);
  - **the cell itself shows only `false`**, with a tooltip listing one score (Value false, Source Api). The cell shows
    one score and the summary averages two;
  - the experiments list counts both: `smoke-1` shows `rubric` **false: 2, true: 2** for 2 trials;
  - the first human score went on `canc-01#0`, the trial the comparison view doesn't show, and the summary didn't move
    at all. A correction is visible in the comparison only if it lands on the latest trial.
- `export` keeps only scores with the evaluators' metadata on the task observation, and reports others as "not
  exported". On `smoke-1` it would report both human scores.

**Annotation queue, tried.**

- `create_queue("p9-review", score_config_ids=[...])` needs at least one score config. The port used the project's
  existing **"pass or fail"** config, a `CATEGORICAL` Pass=1 / Fail=0 created with the project; none was created.
- `create_queue_item(object_type=TRACE)` added two run-1 trials (`canc-01#0`, `#1`). The UI lists both as Pending,
  with Settings and an Annotation panel, and "Process queue".
- **Not completed.** Annotating is a UI action outside read-only. From the queue's config, a score given there would
  be named "pass or fail" with `source: ANNOTATION`, not a second `rubric`. So unlike an SDK score, it wouldn't be
  averaged into the evaluator's `rubric` column. Not verified.
- To check: process the queue, score one trial, and see whether "pass or fail" shows as its own column in the
  comparison.

**Datasets, tried:** upsert by id, item versions on every re-upload, and no version recorded on runs (above). I did not
try editing an item in the UI or running against an older version.

**CI, not tried end to end.**

- `run_experiment` returns per-item evaluations in-process, so a script can gate on its own counts. That is what `run`
  prints, and it doesn't depend on the server.
- From source: the SDK has `RunnerContext` and `RegressionError` for the `langfuse/experiment-action` GitHub Action. A
  user's `experiment(context)` raises `RegressionError(result, metric, value, threshold)`, and the action fails the
  workflow and comments on the PR.
- The SDK's `release` defaults to the first CI commit env var it finds (`GITHUB_SHA`, `CI_COMMIT_SHA`, …). None was
  set here.
- A gate on the UI's comparison summary would gate on one trial per item.

**Hosting:** cloud (Hobby plan). Langfuse is also open source and self-hostable (P0's notes). Retention wasn't checked.

## Friction

In order, with time lost:

1. **No repetitions** (10 min). P0 knew; the open question was whether repeating items in `data` collapses. It doesn't
   (`probes.py reps`), but the comparison view then shows one trial per item.
2. **The run name is the experiment's identity** (5 min, source). The same `run_name` on the same dataset is the same
   experiment, so a retried run would merge into the first. `run` refuses existing names.
3. **Evaluators get only I/O** (10 min). No trace and no run tree, so the transcript rides in the output, stored five
   times per trial. A read-back would race.
4. **Unexpected generations** (15 min). The SUT's model calls showed up as Langfuse generations through the Anthropic
   SDK's own tracing, not Langfuse's. Working out where they came from, and that content needs a separate env var,
   took reading the Anthropic SDK.
5. **An SDK parameter the server rejects** (2 min). `observations.get_many(parse_io_as_json=True)` returned 400:
   "parseIoAsJson=true is no longer supported on the v2 observations endpoint". So I/O always comes back as raw JSON
   strings, and so do experiment items' `input`/`output`.
6. **Thin score reads** (10 min).
   - The items' `scores` field and the default `scores.get_many` return no metadata, comment, trace or observation id.
     They need `fields=details,subject`.
   - `scores.get_many(experiment_id=…)` returned **0** for these runs: the evaluator scores are on observations and
     carry no experiment id.
   - Scores also have `environment: "default"` while their traces have `sdk-experiment`.
7. **Metadata comes back flattened and as strings** (3 min).
   - `rep: 1` is read as `"1"`.
   - Nested dicts become dotted keys: `fault-01`'s `faults` comes back as `faults.tool_error.call: "1"` and
     `faults.tool_error.tool: "get_order"`.
   - An empty `faults: {}` disappears.
   - So the metadata read back is not the dict that was written. The dataset item itself keeps its nested metadata.
8. **Strict pyright** (10 min). The evaluator type's `metadata: Dict | None` and the invariant `List` in
   `ExperimentData` reject ordinary signatures and local dict data, so both are typed `Any`.

The dataset, `run_experiment`, the Anthropic generations, scores and the trace UI all worked first time. P0's
`format()` emoji crash on cp1252 was avoided by not calling `format()`.

## What leaks

This covers what was sent to Langfuse, and anything else that left the machine.

**To Langfuse (`cloud.langfuse.com`):**

- **Dataset `p9-slice`:** 10 items: the email, the full expected dict (the answer key), case id, faults, suite and tags
  (8 kB as read back).
- **Per experiment** (`p9-run-1`, read back by `audit.py`: 2.28 MB as JSON):

  | Observations | Count | What they hold | Size (run 1) |
  | --- | --- | --- | --- |
  | judge generations (under `rubric_v2`) | 90 | the judge's full prompt (policy included, 90 copies), the verdict text, model, effort, tokens, cost, and the span attributes below | 786 kB (34%) |
  | SUT generations (under the task) | 75 | the full message history every turn: **the system prompt** (75 copies), the email, tool calls and results; the response | 512 kB (22%) |
  | evaluator observations | 90 | each evaluator's input (the item input, **the task output with the transcript**, expected output, item metadata) and its evaluations | 452 kB (20%) |
  | task and root spans | 60 | the email, the task output with the transcript, item and run metadata, `rep`, SUT cost | 260 kB (11%) |
  | scores | 180 | name, value, the critique as comment, metadata | 130 kB (6%) |
  | tool observations | 49 | replayed tool calls: arguments, results, turn, error level | 85 kB (4%) |
  | evaluation spans | 30 | counts | 45 kB (2%) |

- **On every observation,** as span or resource attributes:
  - the OTel resource: `service.name: "unknown_service:python.exe"` (the interpreter's name), a random
    `service.instance.id`, and the OTel SDK version;
  - the experiment's ids, name, metadata and the item's metadata;
  - **the Langfuse public key**, on every observation from the Langfuse SDK's scope (229 in run 1). It is the public
    half of the key pair and is sent in a header anyway; the secret key appears nowhere.
- **On every generation**, from the Anthropic SDK's span:
  - **`anthropic.organization.id` and `anthropic.workspace.id`**, the Anthropic account's organization and workspace
    ids, read from response headers (165 each in run 1);
  - `anthropic.request.id` and `gen_ai.response.id`;
  - **`url.full`/`server.address`: the Vessel proxy address `127.0.0.1:4550`**, and the Vessel path with its tag
    (`/b/anthropic/t/p9-langfuse`). Without Vessel this would be `api.anthropic.com`. The local Vessel session and tag
    *headers* are not stored.
- **Exceptions** (`probes.py errors`):
  - a raising task's span carries an OTel `exception` event with `exception.stacktrace`, the full Python traceback with
    absolute file paths. The SDK exports it; I captured it locally with export off first. Here the frames are on the
    repo's drive, outside the home directory (no username). A project under the home directory would send the
    username;
  - uploaded (`errors-1794868594`), Langfuse's API returned only `level: ERROR` and the message ("task failed on
    purpose") as `status_message` and output. No observation field held the stack trace or a path. Whether the server
    keeps the event anyway isn't visible from the API;
  - a raising evaluator records no exception event: the runner catches it inside the span.
- **Not found**, counting strings in everything fetched back for `p9-run-1` (observations, scores, dataset):
  - the Windows username, `Users\`/`Users/`, the checkout's folder name or absolute path;
  - the secret key, `sk-ant`;
  - `X-Vessel` headers;
  - git commit or author.

  Unlike Braintrust, no caller file path is attached to spans. Unlike LangSmith, no git metadata or env vars go into
  run metadata.

**Keys:** the Langfuse key pair goes as Basic auth (REST) and in OTLP export headers, to `cloud.langfuse.com` only.
Nothing was stored in Langfuse as a model key or LLM connection, and no server-side evaluator was configured. The
Anthropic key went only to Vessel/Anthropic.

**To Anthropic, added by having Langfuse loaded.** The Anthropic SDK's OTel propagation injects **`traceparent`** and
**`baggage: langfuse_trace_id=<trace id>`** into every request:

- the SUT's (Vessel request headers, e.g. `trial-canc-01-0`);
- the judge's (21784).

The request bodies are unchanged. `ANTHROPIC_OPEN_TELEMETRY_PROPAGATION=false` would stop it (from source; not tried).
Nothing else changes on the wire.

**Telemetry:** none found in the Langfuse SDK beyond the uploads. There is no analytics client in the package.
`run_experiment` calls `GET /api/public/projects` once to build the experiment link.

**Anthropic API, through Vessel:** 169 SUT calls (sessions `p9-langfuse-<run>`, `p9-langfuse-probe`) and 186 judge
calls (tag and session `p9-langfuse`).
