# P9 in LangSmith (`langsmith` + `openevals`, hosted, EU region)

```bash
cd tools/langsmith && export ANTHROPIC_API_KEY="$(powershell.exe -NoProfile -Command "[Environment]::GetEnvironmentVariable('ANTHROPIC_API_KEY','User')" | tr -d '\r\n')" && export LANGSMITH_API_KEY="$(powershell.exe -NoProfile -Command "[Environment]::GetEnvironmentVariable('LANGSMITH_API_KEY','User')" | tr -d '\r\n')" && export LANGSMITH_ENDPOINT=https://eu.api.smith.langchain.com VESSEL_URL=http://127.0.0.1:4550 && uv run python p9.py run p9-run-1 && uv run python p9.py export p9-run-1-7a47ed79
```

`run NAME` prints the experiment's full name: LangSmith appends a random suffix to the prefix (`p9-run-1` became
`p9-run-1-7a47ed79`), and `export`, `compare`, `queue` and `review` take that full name. The command above exports run
1 by its recorded name; after a fresh `run`, pass the name it prints instead.

Other subcommands:

- `p9.py dataset` uploaded the slice once, as the workspace's `p9-slice` dataset.
- `p9.py run p9-run-2` made the second experiment (`p9-run-2-3ef9f2df`).
- `p9.py export p9-run-2-3ef9f2df --out p9_results_run2.jsonl` exported it.
- `p9.py compare p9-run-2-3ef9f2df p9-run-1-7a47ed79` prints what LangSmith stores for the comparison.
- `p9.py queue p9-run-1-7a47ed79` put two trials in an annotation queue.
- `p9.py review EXPERIMENT --key K` adds one human score through the SDK and prints what the stats do with it.

`VESSEL_URL` is optional. The agent and the judge both run locally on the Anthropic API. LangSmith receives only what
the SDK traces.

**Which file is which.** `p9_results.jsonl` is run 1 (`p9-run-1-7a47ed79`), the record run. `p9_results_run2.jsonl`
is run 2 (`p9-run-2-3ef9f2df`), which exists for the comparison. Both are exported from what LangSmith stored: root
runs, their child runs, and the feedback on them.

## Case is…, Grader is…, Run is…

**A case is a dataset example.**

- `p9.py dataset` writes each slice line as an `Example`:
  - `inputs = {"email"}`;
  - `outputs` = the whole expected dict, which the evaluators see as `reference_outputs`;
  - `metadata` = case id, faults, suite and tags.
- The example id is `uuid5(NS, case_id)`, so a re-upload updates rather than duplicates. LangSmith ids must be UUIDs.
- `aevaluate(data="p9-slice")` iterates the dataset. The runner then copies each example's metadata into its run's
  metadata, prefixed `ls_example_` (`ls_example_case_id`, `ls_example_faults`, …).
- The experiment records the `dataset_version`, and each run records the `example_version`.

```python
examples = [
    {
        "id": uuid.uuid5(NS, r["id"]),
        "inputs": {"email": r["input"]},
        "outputs": r["expected"],
        "metadata": {"case_id": r["id"], "faults": r.get("faults", {}), "suite": r["suite"], "case_tags": r["tags"]},
    }
    for r in rows
]
```

**The target** is `async (inputs, metadata) -> dict`.

- The runner passes the example's fields by parameter name (`inputs`, `attachments`, `metadata`). So `faults` and
  `case_id` come from `metadata` and never reach `inputs`.
- It calls `supportdesk.arun` and returns `trial.output`, the close_ticket call.
- It also writes into the run's metadata:
  - the repeat number;
  - the store outcome;
  - the judge's `actions` and `happened`, built by P4's `view()`;
  - the number of tool runs it replayed.

```python
rep = REPS[RUN_ID[0], case_id]  # LangSmith passes no repetition index; the port counts
trial = await supportdesk.arun(inputs["email"], metadata["faults"], case_id=case_id, rep=rep, run_id=RUN_ID[0])
rt.metadata.update(
    tool_runs=replay_tools(trial.messages),
    status=trial.status,
    outcome=trial.outcome,
    actions=v["actions"],
    happened=v["happened"],
    sut_cost_usd=cost(trial.calls),
)
```

**A grader is an evaluator**: a function whose parameters the runner fills by name (`run`, `example`, `inputs`,
`outputs`, `reference_outputs`). It returns `{"key", "score", "comment"}`, or `{"results": [...]}` for several keys.
Each result is stored as **feedback** on the run.

- **A raising evaluator is caught** (seen in `path-synth`). LangSmith stores a feedback row with `score: null`,
  `comment` = the exception's repr, and `extra.error: true`. The experiment's stats count it under `errors`, not as a 0.
- **A `None` score is stored** as a feedback row with `score: null`. The stats show `n` counted and `avg: null`. The UI
  shows the cell as "No feedback".
- `aevaluate`'s declared evaluator type doesn't admit these signatures under strict pyright, so the list is typed
  `list[Any]`.

```python
def action(outputs: JSON, reference_outputs: JSON) -> JSON:
    ok = [reference_outputs["action"], *(a["action"] for a in reference_outputs.get("also_ok", []))]
    got = outputs.get("action")
    return {"key": "action", "score": got in ok, "comment": f"got {got}, accepted {ok}"}
```

**A run is an experiment**: `aevaluate(target, data=..., evaluators=[...], experiment_prefix=..., num_repetitions=3,
max_concurrency=10, metadata=..., description=...)`.

- An experiment is a tracing project linked to the dataset.
- Each trial becomes one trace: the target's root run, with `llm` and `tool` child runs.
- Each evaluator call becomes a separate trace in a different project, **`evaluators`**, shared by every experiment in
  the workspace. It is linked back only through the feedback's `feedback_source.metadata.__run.run_id`.
- `aevaluate` returns `AsyncExperimentResults`, which must be read with `async for`. A plain `for` raises `TypeError`.

## Native vs glue

**Free from LangSmith:**

- hosted datasets, with dataset and example versions recorded on every experiment and run;
- repetitions (`num_repetitions`);
- concurrency;
- evaluator isolation (an exception becomes an errored feedback row);
- the run tree, which is **handed to the evaluator in memory** with its `child_runs` (see Trajectory);
- `wrap_anthropic` for the SUT's model calls, with tokens and cost;
- feedback with comments;
- the `evaluators` traces of every judge call;
- server-side aggregates;
- the comparison UI;
- annotation queues;
- `create_feedback` for human review;
- the web UI.

**From openevals:** `create_async_llm_as_judge` (prompt template, `system`, a `score` tool for the verdict, a reasoning
field), and its own tracing.

**Glue:**

- restricting the git metadata (a monkeypatch);
- wrapping supportdesk's client (a monkeypatch of `supportdesk.task._anthropic`; no file in supportdesk changes);
- `replay_tools`;
- the repeat counter;
- the rubric wrapper that ANDs three judges;
- the read-back export (rebuilding the transcript from tool runs, mapping feedback to evaluator runs, cross-checks);
- `compare`, `queue` and `review`;
- the CLI.

`path` is written against LangSmith's run model. It is a rewrite of `looked_up_first`, not a call to it.

The export is again the largest piece, as in Braintrust. LangSmith stores everything, but reading back "one row per
trial" means four steps:

1. Group child runs by trace.
2. Take the case id from `ls_example_case_id`.
3. Take the repeat number from the metadata the target wrote.
4. Keep only feedback whose source is an evaluator, so a human score on the same key can't silently change the export.

## Trajectory access

**The tool calls are child runs. The path evaluator reads them straight off the run tree the runner hands it.**

- `replay_tools` writes each tool call that ran as a `tool` child run of the target's run:
  `trace(name, run_type="tool", inputs=args, metadata={turn, call_id, ms})`, ended with `outputs={"result": ...}` and
  `error=` set when the tool errored.
- The evaluator's `run` parameter is the in-memory `RunTree` the target just produced, `child_runs` included. **There
  is no read-back from the server.** So the read-after-write race Braintrust's `trace.get_spans()` had cannot happen
  here.
- `path` still fails closed: if the tree holds a different number of tool runs from the `tool_runs` count the target
  wrote, the score is `None`.
- **Checked on failing paths, through the hosted service.** I put the six synthetic transcripts from the Braintrust
  record through a model-free hosted `aevaluate` (`path-synth`). `p9.path` and `looked_up_first` agreed on all six:
  - fail: refund before any lookup;
  - fail: lookup and refund in the same turn;
  - fail: errored lookup, then refund;
  - fail: lookup of a different order, then escalate;
  - pass: ids reused across turns and order id `" a1 "`;
  - pass: a refund listed after `close_ticket` that never ran.
- On the record runs, `export` rebuilds the transcript from the **stored** tool runs. Run against it, the reference
  `looked_up_first` agrees with the stored `path` feedback on all 60 trials.
- **Tool runs come back with JSON keys sorted.** The judge's `actions` text rebuilt from them matches what the target
  sent as JSON in 30/30 per run, but byte-exact in 0/30.
  - Unlike Braintrust, `59.0` stays `59.0`.
  - Only the key order changes.

**Native for the model calls: `wrap_anthropic`.**

- It wraps one client *instance*. LangSmith has no global patch for the Anthropic SDK (its `integrations` cover the
  Claude Agent SDK, OpenAI Agents and others, not plain `anthropic`).
- So the port replaces supportdesk's cached client factory with one that returns `wrap_anthropic(client)`. That is
  glue, but supportdesk's files are unchanged.
- Each `messages.create` becomes an `llm` child run, by contextvars, because `arun` awaits in the target's task.
  - A sync target calling `supportdesk.run` would hop to supportdesk's background loop thread. The `llm` runs would
    probably lose their parent. Not tried.
- **What a stored `llm` run holds:**
  - the request kwargs as inputs, with **the system prompt moved into `messages` as a leading `{"role": "system"}`
    message**, plus `tools`, `max_tokens`, `output_config` and **`extra_headers`** (see What leaks);
  - the response **reshaped to OpenAI form**: `content` is the text (or `null`), `tool_calls` carry
    `function.arguments` as a JSON *string*, and **thinking blocks are dropped** from the output. They survive only as
    history in the next call's input, 32 blocks in run 1;
  - `usage_metadata`;
  - a `total_cost` that LangSmith computes itself, at the same Haiku 5.5 price as `PRICES`.
- Checked against Vessel: `wrap_anthropic` doesn't change the request. A SUT request from run 1 (21310) has the same
  header names and body keys as one from the Braintrust port (20882), and `system` is still a string on the wire;
  only LangSmith's stored copy moves it into `messages`.
- As with Braintrust, a tool's result exists in the `llm` runs only as a `tool_result` block in the next call's input.
  So the replayed tool runs are what the path evaluator uses.

## The judge

**openevals' `create_async_llm_as_judge`, one per v2 criterion.**

- `rubric()` gathers the three and returns four feedback keys: `rubric`, `accurate`, `no_outside_promises` and `tone`.
  `rubric` is true only if all three pass, and `None` if any judge raised.
- The judge sees the target's own `actions`/`happened` from run metadata, the email (`inputs`), the reply (`outputs`)
  and the policy (a prompt variable).
- No reference output is passed: no answer key reaches the judge.

```python
JUDGES = {
    name: create_async_llm_as_judge(
        prompt=USER, system=RUBRIC_SYSTEM_V0.format(criterion=text), judge=judge_model(), feedback_key=name
    )
    for name, text in V2.criteria.items()
}
```

**It keeps P4's system/user split**, which Braintrust's `LLMClassifier` couldn't.

- `system=` is P4's `RUBRIC_SYSTEM_V0` with the criterion. openevals prepends it unformatted, as the system message.
- The user template is P4's own `<data>` fences around `str.format` variables. openevals `.format()`s it.
- **Parity, checked on what LangSmith stored** (`judge_crosscheck.py`, part 1): all 90 judge prompts of run 1 have one
  of the three P4 system prompts, and a user message equal to `rubric_prompt(view(...), answer=False)`, byte for byte.

**What it sends.** Vessel request 21364 is in `p9_judge_prompt.txt` in full.

| Param | Value | From |
| --- | --- | --- |
| system | P4's rubric system prompt, criterion filled in | openevals `system=` |
| user | P4's user block: policy, email, tool calls and results, what changed, the reply, each in `<data>` fences | template |
| tools | one tool `score {reasoning: string, score: boolean}`, both required, `additionalProperties: false` | openevals' default schema (`use_reasoning=True`) |
| tool_choice | `{"type": "tool", "name": "score"}`, **forced** | langchain-anthropic forces it on Haiku 5.5 (on Opus 5.5 in P0 it left it out) |
| max_tokens | 8000 | set on `ChatAnthropic`; without it, the model profile's maximum |
| thinking / effort | not sent; `thinking_tokens: 0` | P4 uses `effort: medium`, not sent here |
| temperature | not sent | |
| user-agent | `langchain-anthropic/1.7.10` | |

**Verdict parsing.**

- LangChain's `JsonOutputKeyToolsParser` takes the `score` tool call's arguments. openevals returns
  `{key, score: bool, comment: reasoning}`.
- The `score` field's description in the tool schema is the only "judge" wording openevals adds: "A score that is true
  if criteria in the prompt are met, and false otherwise…". `reasoning` carries "You MUST end the reasoning with a
  sentence that says: Thus, the score should be: SCORE_YOU_ASSIGN."
- P4's system prompt ends "decide: passed is true if the reply meets it", but the tool field is called `score`. The
  model maps one to the other without trouble.
- The reasoning becomes the feedback's `comment`, visible on the run in the UI.

**What it drops or adds:**

- **Drops** P4's structured `Verdict{critique, passed}` and `effort`.
- **Adds** the tool and its descriptions.
- **Output:** 241 output tokens per call on average, against P4's 207 on the same replies.
- **No prompt caching:** none requested, none used.

**Can it fail a reply?**

- Yes. It failed 4 of 60 trials across the record runs (below).
- On the reference's two failing replies (`judge_crosscheck.py`, part 3), it fails both, as the reference did:
  - `dig-01#2` fails `accurate` (the invented download timing);
  - `win-01#2` fails `no_outside_promises` (the offered replacement part).
- Braintrust's autoevals judge passed `dig-01#2`.

## Repeats / pass@k

**Repetitions are native; the repetition index isn't; pass@k isn't.**

- `num_repetitions=3` chains the dataset three times.
- The runner passes no index to the target and stores none. The project only records `num_repetitions: 3` in its
  metadata.
- Without the target's own counter (`rep` in run metadata), a case's three trials are told apart only by start time.
- The comparison UI groups the three repetitions under one example row, with a `1/3` pager and a `µ` mean per
  feedback key.
- The experiment's stats are a mean over feedback rows.
- pass@3 / pass^3 would be glue over the export.

## The experiment comparison (hosted)

**How it is set.**

- The UI's compare view is per dataset: select experiments, and it labels them `A` and `B`. Here run 2 was `A`, and
  run 1's cells were marked against it. `p9.py run` prints the link to a one-experiment view.
- `aevaluate` takes no baseline (Braintrust's `base_experiment_name` has no equivalent), and no SDK call returns a
  diff.
- `p9.py compare` reads the two sources the view is built from:
  - `read_project(include_stats=True)` for each experiment's aggregates;
  - `POST /datasets/{id}/runs` with both session ids, for the per-example runs side by side. That is the endpoint
    behind the SDK's `get_experiment_results`, which is marked deprecated.

**What it showed for run 2 against run 1** (UI, read-only, through Claude in Chrome, already signed in):

- **Charts:** feedback averages per key, P50/P99 latency (4.62 s both), tokens (149,423 vs 149,824) and cost
  ($0.0207 vs $0.0208, SUT only: the judge's runs live in `evaluators` and are not counted). These run stats moved
  later too: 20 minutes after the runs, `read_project` gave 147,700 / $0.0205 and 147,579 / $0.0204. The latter
  matches the SUT tokens the export sums from the stored `llm` runs exactly.
- **The table:** one row per example. For each experiment, the first output with a `1/3` pager, and per feedback key a
  `µ` mean over the three repetitions.
  - `dig-01`'s `accurate` was highlighted red: run 1 0.33 against run 2 1.00.
  - The `accurate` header showed `↑0 ↓1`.
  - `fault-01` (0.67 in both) was not flagged.
- **The headers were wrong for the first quarter hour.** Each column header shows an average and an "N received"
  count. Looked at about 5 minutes after the runs, they showed:
  - run 2: **`accurate` 1.00 AVG, 17 received**;
  - run 1: **0.89, 9 received**;
  - some columns also badged **"Partial"**. The tooltip says 17 feedback items were received and the average may
    change while runs or evaluators are incomplete.
  
  The true values are 29/30 = 0.97 and 27/30 = 0.90 over 30 runs each. Run 2's own `fault-01` row in the same table
  shows `accurate` 0.67.
- **The stored aggregates lag the feedback by 10–15 minutes.** `read_project(include_stats=True).feedback_stats`
  matched the UI's headers:
  - n=9 for every key of run 1 and n=17 for run 2, unchanged from 4 to 11 minutes after the runs ended;
  - complete at **14 minutes**: n=30, run 1 `rubric` 0.90 and run 2 0.967, matching the export.
  
  Meanwhile `list_feedback` returned all 180 rows for each run, every one with the experiment's `session_id`.
  - `smoke` (2 trials) had empty stats for 10–13 minutes; `endpoint-check` (1 trial) was still empty at 13 minutes
    and filled in by 16.
  - The model-free `path-synth`, and the human scores added to it, were counted within 2 seconds. So the delay is not
    fixed; it seems to follow how the runs were ingested, which I can't see.
  - The run-level data (rows, per-example `µ` cells, feedback) was complete as soon as `aevaluate` returned. Only the
    aggregates lag.
  - It means **the headline numbers of a fresh experiment can't be trusted for a while**, and a CI gate on
    `feedback_stats` right after a run would read partial numbers without an error. The "Partial" badge and the
    "received" count are the only signal.
  - The `error_rate` counts root runs only: an errored child tool run left it at 0.0 in `path-synth` and in both
    record runs.

**How it treats run-to-run noise:**

- **It pairs by example, not by trial**, and compares the mean over repetitions, as Braintrust does.
- **No noise model.** There are no intervals or significance tests, and any lower mean is a regression:
  `dig-01` 1.00 → 0.33 got the red cell and the `↓1`. That is one trial of three moving, on a borderline phrasing that
  P4's judge scores the other way.
- **Errors don't add noise here.** Unlike Braintrust, an errored child run (`fault-01`'s injected tool error, the
  refused `close_ticket` in run 1) does not touch the experiment's `error_rate`, which stays 0.0. So the comparison
  didn't flag those cases.
- **Cost and tokens are SUT-only** (above), and identical-config runs differ by a few hundred tokens. The UI shows them
  as numbers with no regression marker.

## Human review, CI story, hosting

**Human feedback through the SDK, tried.**

- `client.create_feedback(run_id, key=…, score=0, comment=…, trace_id=…)` stores a feedback row with
  `feedback_source.type = "api"`, next to the evaluator's row (`type = "model"`). Nothing marks one as overriding the
  other.
- **It is averaged in, not substituted.** I put it on the model-free `path-synth`, whose stats were complete, so the
  effect could be measured:
  - one human `path: 0` on a run the evaluator scored 1 took `path` from **n=6, avg 0.333 to n=8, avg 0.25**. The 8
    includes an earlier agreeing human 0 on another run (n=7, avg 0.286);
  - the stats updated within 2 seconds;
  - so every feedback row is one more sample on its key. A correction dilutes the judge rather than replacing it, and
    the key's `n` stops being the number of trials;
  - the run's own cell in the UI showed **`µ 0.50`**, the evaluator's 1 and the human's 0 averaged, not colored as a
    fail.
- `export` reads only evaluator feedback. It reports any other feedback on an exported run as "not exported".

**Annotation queue, tried.**

- `create_annotation_queue("p9-review")` and `add_runs_to_annotation_queue` put two run-1 trials (`canc-01#0`, `#1`)
  in a queue (`p9.py queue`).
- In the UI (read-only), the queue shows each trial as a conversation: the email, the LLM call with tokens and cost,
  and the tool calls. A reviewer pane offers "Next (mark as completed)" and "Add to Dataset".
- The queue's rubric holds only a free-text **note**, because the queue was created without `rubric_items`.
  - Scoring `rubric` pass/fail there needs a rubric configured on the queue, or a feedback config. A feedback config is
    a workspace setting, so I left it.
  - I didn't complete a review in the UI. A score given there would presumably be a feedback row like the SDK's (not
    verified).

**Datasets, tried:** described above (versions, example ids, metadata copied onto runs). Re-running `p9.py dataset`
with unchanged content kept 10 examples (the uuid5 ids made it an update) but **created a second dataset version**, so
experiments run before and after a no-op re-upload record different `dataset_version`s. I did not try editing an
example in the UI or pinning an older version.

**CI, not tried end to end.**

- `aevaluate` returns per-row results in-process, so a script can gate on its own counts. That is what this port's
  `run` prints, and it doesn't depend on the server.
- A gate on the server's `feedback_stats` run right after `aevaluate` would have read n=9 or n=17 here; the stats were complete only 14 minutes later (above).
- LangSmith's pytest plugin (`langsmith.testing`, `@pytest.mark.langsmith`) is the documented CI route. Not tried.
  From source:
  - it also writes `ls_env.get_git_info()` (author name and email included) into experiment metadata;
  - it names the test suite after the repo directory;
  - it tags dataset versions `git:commit:<sha>`.
- The UI shows a banner on every page: "76 days left to migrate off deprecated API endpoints … your API key … still
  calls 5 deprecated endpoints, which stop working on January 31, 2027." It went from 3 to 5 as this port ran; the
  banner doesn't name them. `list_runs` and `get_experiment_results` are marked deprecated in the SDK
  (`LangSmithDeprecationWarning` on every `list_runs`), and the replacement, `client.runs.query`, needs explicit
  `selects`. I didn't migrate. A CI script written against this SDK's main read calls has a fixed expiry.

**Hosting:** cloud. Self-hosting is Enterprise (P0). The free tier's trace retention is 14 days for "shortlived"
traces (server `info`: `trace_tier_duration_days`).

## Friction

In order, with time lost:

1. **Git metadata** (10 min, source). `evaluate`/`aevaluate` add `ls_env.get_git_info()` to every experiment's
   metadata:
   - `remote_url`, `commit`, `branch`, `tags`, `dirty`;
   - **the last commit's `author_name` and `author_email`**;
   - `repo_name`.
   
   There is no argument or env var for it. The port replaces `ls_env.get_git_info` before any run. The stored project
   metadata confirms only `commit`, `branch` and `dirty` went up, plus `revision_id` (`git describe --tags --always
   --dirty`, a separate call).
2. **No global Anthropic patch** (5 min). `wrap_anthropic` wraps an instance, so supportdesk's cached client factory is
   replaced at import (glue).
3. **`AsyncExperimentResults` is async-only** (1 min). `for row in res` raises `TypeError`; it needs `async for`.
4. **Example metadata comes back renamed** (3 min). `case_id` is `ls_example_case_id` on the run.
5. **No repetition index** (5 min, source). The runner chains the examples three times and labels nothing.
6. **Evaluator traces live in another project** (10 min). Every judge call goes to the shared `evaluators` project. The
   only link from a feedback row to its evaluator run is `feedback_source.metadata.__run.run_id`. The feedback rows
   carry no `source_run_id`.
7. **Stored JSON keys come back sorted** (5 min). Byte-exact rebuilds of the judge's tool-call text fail; JSON-equal
   ones pass.
8. **Strict pyright** (15 min). Most `Client` methods take or return bare `dict`, so every call is "partially unknown".
   The port goes through an `Any`-typed client.
9. **Lagging `feedback_stats`** (15 min). The aggregates were partial for about 14 minutes after each run. See the comparison.
10. **Deprecated read API** (no time lost yet). `list_runs` warns on every call and the UI nags; the replacement needs
    `selects`.

The dataset, `aevaluate`, repetitions, the openevals judge (with a system prompt), feedback and the run tree all
worked first time.

## What leaks

This covers what was sent to LangSmith, and anything else that left the machine.

**To LangSmith's EU API (`eu.api.smith.langchain.com`):**

- **Dataset `p9-slice`:** 10 examples: the email, the full expected dict (the answer key), case id, faults, suite and
  tags (7 kB).
- **Per experiment** (`p9-run-1`: 4.9 MB as fetched, ids included). Each judge prompt is stored about four times
  over, which is why the evaluator traces are nearly three quarters of it:

  | Runs | Count | What they hold | Size (run 1) |
  | --- | --- | --- | --- |
  | `evaluators`: chains (`rubric`, `llm_as_*_judge`, `RunnableSequence`, `action`, `path`) | 270 | each evaluator's inputs (the full run and example, or the formatted prompt) and outputs | 1.41 MB (34%) |
  | `evaluators`: `llm` (judge) | 90 | the whole judge prompt (policy included, 90 copies), invocation params, the tool, the response with reasoning | 1.16 MB (28%) |
  | experiment: `llm` (SUT) | 75 | the full Anthropic request every turn: messages with tool results and thinking blocks, **the system prompt** (75 copies), tool schemas, **`extra_headers`**, `output_config`; the reshaped response, tokens, cost | 0.59 MB (14%) |
  | `evaluators`: parser | 90 | the judge's raw message again | 0.49 MB (12%) |
  | experiment: root (`AsyncTarget`) | 30 | the email, the close_ticket output, metadata (example metadata, rep, outcome, the judge's `actions`/`happened`, SUT cost) | 0.24 MB (6%) |
  | feedback | 180 | key, score, the judge's reasoning as comment | 0.18 MB (4%) |
  | experiment: `tool` | 48 | replayed tool calls: arguments, results, turn, error | 0.11 MB (2%) |

- **On every run**, in `extra`:
  - `runtime`: SDK and LangChain versions, `platform` (`Windows-11-10.0.26300-SP0`) and the Python version. No
    hostname or username.
  - `metadata`: every `LANGSMITH_*` and `LANGCHAIN_*` env var whose name doesn't contain key, secret, token, password,
    pwd, credential or email. Here that is **`LANGSMITH_ENDPOINT`**, on every one of the ~600 runs per experiment (153 in the experiment, 450 in `evaluators`).
  - the experiment's `metadata` dict (judge, rubric, k, port) and `revision_id`.
- **`wrap_anthropic` uploads the request's `extra_headers` verbatim.** supportdesk passes Vessel's tags there
  (`X-Vessel-Tags: sut,trial-…`), so 75 `llm` runs per experiment carry them. The wrapper redacts MCP server auth but
  not headers. An auth or beta header passed per request would go up the same way. The client's `default_headers`
  (Vessel's session) and `base_url` are not stored.
- **Experiment metadata:** `git` restricted as above (branch, commit, dirty), `revision_id`, `dataset_version`,
  `num_repetitions`, `__ls_runner`.
- **Errors:** a raising target is stored with `error` = its repr plus `NoneType: None`
  (`target-error`). The traceback is formatted outside the `except` on this async path, so it comes out empty, and no
  frame or file path goes up. A raising evaluator's run is not stored at all: its feedback names a run id that returns
  404, and the only trace of the error is the feedback comment, the exception's repr.
  - **From source, not tried:** `utils._format_exc` drops frames containing `langsmith/` with a forward slash. A sync
    traced function that raises inside an `except` would upload a full traceback, and on Windows no frame would be
    filtered: paths with the username would go up.
- **Not found**, checked by counting strings in everything fetched back for `smoke`, `endpoint-check`, `p9-run-1`,
  `p9-run-2` and `path-synth`, plus the `target-error` run's error (runs, evaluator runs, feedback, dataset, project):
  - the Windows username, `Users\`/`Users/`, the drive path or worktree path;
  - the git author name or email, `remote_url`;
  - the hostname, `127.0.0.1`;
  - either API key, `sk-ant`, `lsv2_`, `x-api-key`.
  
  Unlike Braintrust, no caller file path is attached to runs.

**Keys:** the LangSmith key goes in `x-api-key` to the EU API only. Nothing was stored as a workspace secret, and no
online evaluator or playground model was configured. The Anthropic key went only to Vessel/Anthropic.

**Telemetry:** none found in the SDK beyond the trace uploads themselves. `GET /info` is called at client start-up
(P0). Its response includes `phone_home_enabled: false`; what that flag covers isn't stated.

**Anthropic API, through Vessel:**

- 156 SUT calls (sessions `p9-langsmith-<prefix>`);
- 195 openevals judge calls (session `p9-langsmith`, via `X-Vessel-Session` on `ChatAnthropic(default_headers=…)`);
- 90 P4 judge calls for the cross-check (tag `p9-langsmith-p4`, no session).
